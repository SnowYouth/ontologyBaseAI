## 写在前面:为什么"懂架构"在 AI 时代越来越值钱

过去区分程序员水平的,很大程度是"能不能把某个功能用代码正确实现"。而在 AI 越来越能写具体代码的今天,这一层的含金量正被快速拉平——纯粹的"实现能力"不再是护城河。

真正稀缺的,是**知道要搭什么、为什么这么搭、每个决策背后在权衡什么**的能力。同样一句"给 agent 加个工具",有人只会照抄一段代码,有人能立刻说清:这个能力该做成 tool 还是 skill?顺序要不要保证?该不该下沉到代码?工具多了会不会 confusion?——这就是架构视角。

本文就是一次这样的复盘:不教你抄代码,而是把 agent 底层那套"软与硬、协议与自觉、归一与分流"的骨架彻底讲透。看懂了,你以后读任何 agent 框架,都能一眼认出"它在解决我这里的哪个痛点"。

## 第一部分:一条贯穿全文的主线 —— 软与硬

整篇文章只有一个核心概念,先立在这里,后面所有内容都是它的展开:

> **在一个 agent 系统里,任何一件事都可以问一句:它是"软"的还是"硬"的?**
> - **软 = 由 LLM 自己决定,是概率行为**,你无法保证,只能通过提示词提高"正确的倾向"。
> - **硬 = 由代码或协议保证,是确定行为**,LLM 没有选择权,该发生的必然发生。

这条主线会反复出现:

| 问题 | 软(LLM 决定) | 硬(代码/协议保证) |
|---|---|---|
| 要不要读某个 skill | ✅ 全凭自觉 | —— |
| 要不要调某个 tool | ✅ 全凭自觉 | —— |
| 一旦决定调,怎么表达 | —— | ✅ 必须用 `tool_calls` 格式 |
| 调了之后会不会真执行 | —— | ✅ 代码一定执行 |
| 多个工具的执行顺序 | ✅ LLM 给的数组顺序不可靠 | 要保证就得下沉到代码 |
| 结果怎么回填给 LLM | —— | ✅ 协议规定的三件套 |
| 工具/skill 的 schema 长啥样 | —— | ✅ 协议规定的外壳 |

**贯穿全文的那句铁律:**

> **凡是"软的、但你要它变确定",唯一的办法就是把它从 LLM 手里拿走,下沉到代码里,把它焊成硬的。**

## 第二部分:skill 与 tool 的本质区别

### 1. 它俩根本不是一个量级的东西

初学时容易把 skill 和 tool 并列看待,好像都是"给 agent 的能力"。但在**约束力**上它们天差地别:

| | tool | skill |
|---|---|---|
| **本质** | 一个**能力**(能读文件、能搜索、能写盘) | 一段**建议**(遇到这种情况,建议你这么做) |
| **对 LLM 的约束力** | 硬:调了就真执行,参数错了真报错 | 软:读不读、读了听不听,全凭 LLM 自觉 |
| **谁保证它生效** | **代码**(dispatch 到实现函数) | **没人**——只有 LLM 的"配合意愿" |

### 2. skill 不是 SOP,是一张便利贴

这是最容易误解的一点。很多人潜意识里把 skill 当成"一套 agent 必须遵守的作业规范(SOP)",于是会担心:"万一 LLM 不读 skill,直接调工具,不按我规定的规范来怎么办?"

**这个担忧完全成立,而且它不是 bug,是 skill 机制的设计本质:**

> **skill 从来不是一个"控制流机制",它是一个"提示注入机制"。它能做的上限,就是"把一段文字塞进 LLM 的注意力范围"。至于 LLM 读没读、照没照做,skill 本身一点强制力都没有。**

- 你以为的 skill:一套 agent 必须遵守的 SOP。
- 实际的 skill:一张便利贴,贴在 LLM 眼前,写着"嘿,这种活儿最好这么干"。便利贴永远只是便利贴。

所以"LLM 万一不读 skill 直接调 tool 呢?"——**它当然可能。skill 在设计上就没打算拦住它。**

### 3. 三根软绳子:为什么它"大体能工作"

既然没有强制力,为什么实践中 agent 大多数时候还是会先读 skill?靠的是三根**概率性**的绳子:

- **绳子① 描述写得好不好(信噪匹配)。** skill 的 description 是你唯一、也是最重要的调控杠杆。写成"**当用户要求 X 时,做 Y**"这样的条件句,比写成"这个技能能做 Y"有效得多——因为 LLM 本质在做模式匹配,条件句直接命中"现在是不是该用它"。
- **绳子② 训练先验。** 主流模型被 RLHF 调过,对"有现成指南就先看指南"有一定倾向。但这最不可靠——换个模型倾向就变。
- **绳子③ 清单的存在感。** 每轮 system 里都拼着技能清单,持续在 LLM"耳边念叨"。

**三根绳子的共同点:全是概率。** 拧一起大概能到 90%,但**永远不是 100%**,而且你无法让它变成 100%——只要决策权在 LLM 手里,就有尾部概率它抄近路。

### 4. 分诊原则:错了会出事的,别交给 skill

把上面的认知落成一条可操作的设计原则:

> **凡是"错了也无所谓"的事,交给 skill(软约束,靠自觉);凡是"错了会出事"的事,必须下沉到代码(硬约束,不给 LLM 选择权)。**

两个对照例子:

- **适合当 skill 的:** "回答时标注信息来源"。LLM 万一没照做,顶多答案少了几个来源标注,**体验差一点,但不出事**。这种"退化但不致命"的事,天生适合 skill。
- **绝不能当 skill 的:** "写文件只能写到某个沙箱目录"。如果你把这写成一段"请不要写到别处"的 skill 文字——**灾难**。只要有一次 LLM 没读、或被绕过,它就能写穿整个磁盘。**安全永远不能建立在"LLM 会自觉读规范"上**,必须是代码里硬邦邦的 `raise ValueError`。

**"平衡 skill 和 tool 好难"这个感觉,一旦按分诊原则就消解了:** 难,是因为你在用一种机制(skill)承担两种性质完全不同的活。按"错了会不会出事"劈成两堆——软的归 skill,硬的归代码——就不纠结了。**skill 不是用来保证正确性的,它是用来提升"正确的默认倾向"的。**

## 第三部分:渐进披露 —— 一个被 caching 逼出来的决策

skill 的正文(完整步骤)往往很长。怎么把它喂给 LLM,有两条路,选哪条不是审美问题,是被一个硬约束逼出来的。

### 1. 两条路:全量注入 vs 渐进披露

- **全量注入:** 把所有启用 skill 的**完整正文**,每轮都拼进 system prompt。agent 一睁眼就看到所有技能的全部步骤,不用额外调工具。
- **渐进披露:** system 里每轮只拼一份**极短的目录**(L1,每个 skill 一行 `name: description`),正文(L2)等 LLM 自己判断"这个技能相关"时,再调一个专门的工具(如 `load_skill(name)`)把它拉出来。

两条路的账:

| | 全量注入 | 渐进披露 |
|---|---|---|
| **省什么** | 省一次 round-trip(不用多调一轮工具) | 省 token(每轮 system 只背几百字目录) |
| **费什么** | 每轮 system 背**所有** skill 正文的全部 token | 用到某 skill 那轮多一次工具往返 |

关键在**"每轮都背"**。agent loop 是个循环,每一轮都要把完整 messages(含 system)重新发给 LLM。全量注入意味着:哪怕这轮只想调个搜索工具,也得连着一堆八竿子打不着的 skill 正文一起,**按全价重新发一遍**。

### 2. 决定性变量:prompt caching

要在这两条路之间选,**唯一决定性的变量是"能不能吃到 prompt caching"**:

- **有 caching 的世界(如某些官方端点):** system prompt 作为固定前缀会被服务端缓存。第二轮起,这段前缀命中缓存,token 成本打到 1/10 甚至更低。这种情况下全量注入**不太亏**——只在第一轮全价付一次,后面都是缓存价。所以能吃到 caching 的项目,常常直接全量塞,图省事、少一次往返。

- **没有 caching 的世界(如经过某些中转/代理层):** 每一轮 system 都是全价新 token,没有缓存。这一下账彻底翻过来:全量注入 = 每轮都全价重付所有 skill 正文,skill 越多每轮固定开销越重,还白占 context window。而一次任务真正用得上的 skill 可能就一两个。

所以在**没有 caching**的前提下,渐进披露几乎是唯一理性选择:**只有用到的 skill 才付它正文的 token,没用到的永远只是目录里的一行。** 多花的那次工具往返,远比"每轮白背 N 份正文"便宜。

### 3. 一句话记住这个取舍

> **全量注入是拿 token 换 round-trip;渐进披露是拿 round-trip 换 token。**
> **有 prompt caching → token 变便宜 → 换 token 划算 → 可以全量。**
> **没有 caching(中转/代理层通常吃不到)→ token 全价 → 必须省 token → 渐进披露。**

这个"token × caching 的天平"是本文最值钱的认知之一,可以拿它去套任何"要不要把 X 每轮塞进 context"的决策。

**两个配套的工程红线(实践中容易踩):**

- **L2 的调出工具必须"上线可见"。** L1 清单是每轮无门控拼进 system 的;如果那个 `load_skill` 工具在上线环境被门控规则过滤掉了,就会出现"看得到技能清单、却没有调出正文的工具"的断链。所以它必须被标成"上线也可用"。
- **L1 清单必须每轮现算,绝不缓存回 system_prompt。** 一旦图省事把清单结果写回固定的 system_prompt,就等于把"首轮那一刻的技能清单"焊死了,之后动态启停 skill 全部失效。清单必须是每轮当场拼接的字符串。

## 第四部分:tool calling 协议 —— 去程与回程

这一部分回答几个最常见的困惑:工具到底怎么发给 LLM?LLM 怎么告诉代码"我要调工具"?这些是不是有正式规范?

**答案总纲:这不是任何单个项目的自创约定,是一套有正式规范、由 API 厂商在服务端和你代码之间共同执行的标准协议——OpenAI 叫它 function calling,Anthropic 叫 tool use,结构同构,现已是行业事实标准。**

### 1. 提示词的真实结构:两条通道

一次带工具的 LLM 调用,发出去的不是一锅,而是**两个独立通道**:

```
通道 A  messages = [ system(系统提示词 + skill 的 L1 清单),  历史对话,  当前 query ]
通道 B  tools    = [ 每个工具的完整 JSON Schema ]     ← 独立参数,不在 messages 里
```

三个常见的认知修正:

- **tools 不在 messages 里。** 它是请求体里和 messages **平级的顶层字段**,既不是 system message 也不是 user message,是第三条通道。所以"工具放在提示词里告诉 LLM"这个直觉是错的。
- **别漏了 history 和 query。** system 只是背景设定,真正驱动这一轮的是历史 + 当前问题。
- **tool 的信息比 skill 详细得多。** skill 在 L1 只给一行 `name: description`;tool 给的是**完整签名**——名字、每个参数的类型、哪些必填、描述全都有。这个详略差是刻意的:

| | 给 LLM 的信息量 | 为什么 |
|---|---|---|
| tool | 完整 schema(全价) | 工具就那么几个,LLM 必须知道**怎么调**(参数),一次给全 |
| skill | 一行 name+desc(极简) | skill 可能很多且正文长,先给"标题",用到再 load(渐进披露) |

### 2. LLM 怎么"知道"自己有哪些工具

这一点有点反直觉:

> **从 LLM 视角看,它确实"读到"了工具描述——但这段描述不是你手写进 prompt 的,是 API 服务端替你注入的。**

过程:

1. 你的代码把 `tools` 数组作为**独立参数**发给 API 服务端。
2. 服务端拿到后,在你看不见的地方,按该模型**训练时约定的特殊格式**,把工具描述注入进模型的输入序列。不同模型注入格式不同(特殊 token / 模板),这套格式是模型**训练时就学过的**。
3. 所以模型"看到"工具,底层和看到 system prompt 一样都是输入 token。但你作为调用方**不需要知道那套注入格式**——只管把结构化 tools 丢进标准字段,服务端负责翻译。

**这就是为什么"结构化 tools 参数"远比"自己在 prompt 里用自然语言描述工具"强:**

| | 手写进 prompt | 走 tools 标准参数 |
|---|---|---|
| 格式 | 你随便写,模型连蒙带猜 | 模型**训练时专门学过**,识别率高得多 |
| 返回 | 模型只能自然语言说"我想调 X",你还得正则解析 | 模型返回**结构化 tool_calls**,直接能用 |
| 参数校验 | 无 | schema 的 required/type 服务端能帮你约束 |

**一句话:function calling 的本质,是"厂商在训练阶段就教会了模型认识 tools 字段、并用 tool_calls 字段回话"。这是模型和 API 双方事先约定好的"暗号",你只是在用它。**

### 3. 回程:tool_calls 字段与代码的分流

发出带 tools 的请求后,LLM 的返回不再是一坨纯文本,而是结构化对象,有两种形态:

**形态 A:决定调工具。** content 可能为空,多出一个 `tool_calls` 数组:

```json
{
  "role": "assistant",
  "content": null,
  "tool_calls": [
    { "id": "call_abc123", "type": "function",
      "function": { "name": "write_file",
                    "arguments": "{\"filename\": \"note.md\", \"content\": \"...\"}" } }
  ],
  "finish_reason": "tool_calls"
}
```

**形态 B:决定直接回答。** 没有 tool_calls,就是纯文本 content,`finish_reason: "stop"`。

**代码就靠"有没有 tool_calls"分流:** 有货 → 逐个执行工具、把结果回填、进入下一轮;没货 → 这是最终答案,直接返回收工。

**关于"有没有 API 规范强制"——要分两层理解:**

- **形式是硬的。** 当 LLM 决定调工具时,它**没法用自然语言随便说**。模型被训练成:一旦要调工具,就输出符合约定格式的特殊序列;服务端**保证**把它解析成规范的 tool_calls JSON。所以"要调工具就必须以 tool_calls 形式出现"是协议保证的,硬。正因如此,代码里那句 `if not tool_calls` 才能成立——你能 100% 相信"没这个字段 = 它没打算调工具"。
- **意愿是软的。** "该调的时候到底调不调"仍是 LLM 自己决定的(接回第一部分的软/硬主线)。

> **协议强制的是"形式",不是"意愿"。想不想调 = 软;只要想调,表达方式就被锁死 = 硬。**

### 4. schema 从哪来:自动派生

工具的 schema **外壳结构是协议规定死的**(不能乱来):

```json
{ "type": "function",
  "function": { "name": "...", "description": "...",
                "parameters": { "type": "object", "properties": {...}, "required": [...] } } }
```

但**内容通常不是手写的,而是从代码自动派生的**。主流做法(Anthropic SDK、LangChain 的 `@tool`、Pydantic-AI 等都是这套)是:你写一个**带类型标注 + docstring 的普通函数**,用反射自动生成 schema——

- 函数名 → schema 的 name
- docstring(通常取第一段)→ description
- 每个参数的 type hint → 翻译成 JSON Schema 的 type
- 没有默认值的参数 → 进 required 数组

**好处:加一个新工具的成本 = 写一个函数。** 你不用维护两份东西(函数一份、schema 一份还怕对不上),schema 是函数的**投影**。

> **外壳结构 = 协议(硬);内容 = 你的函数"长出来的"(你写函数,代码反射生成,你没手写 JSON)。**

代价:自动派生通常只取 docstring 第一段、只支持有限的几种基础类型。生产级派生会支持嵌套对象、枚举、复杂模型——这是个已知的可扩展点。

### 5. 结果回填的三件套硬约定

工具执行完,结果要回填给 LLM,格式是协议硬约定:

```json
{ "role": "tool", "tool_call_id": "call_abc123", "content": "..." }
```

三个字段的"硬"程度不同:

- **`role: "tool"` —— 硬。** 缺了它或写成别的 role,服务端校验消息序列时**直接报 400**。协议规定"assistant 发起 tool_calls 后必须有对应 role=tool 的回应"。
- **`tool_call_id` —— 硬,且双重。** 结构上缺了可能 400;**语义上更要命**——LLM 一轮可能点多个工具,它靠这个 id 把"结果"和"当初点的哪一单"配对。id 填错但结构对 → **不报错,但 LLM 把 A 的结果当成 B**,这种 bug 比直接报错难查一百倍。
- **`content` —— 内容软,存在硬。** 里面写 JSON 还是纯文本都行,但**必须有**。

**一个关键推论:失败也必须回填。** 工具执行炸了(参数错、文件不存在、沙箱拒绝),**不能跳过回填**,而要把错误信息包成合法的 content 发回去,例如 `{"error": "..."}`。原因有二:① 让 LLM 看到失败、下一轮自我纠正;② **协议要求每个 tool_call 都必须有对应结果**,漏回填某个 tool_call,下轮请求会因"悬空的 tool_call"直接报错。

> **role + tool_call_id + content 三件套是协议硬约定。缺 role 或 id → 400;id 填错 → LLM 配对错乱(更阴);漏回填 → 下轮报悬空 tool_call。所以"连失败都要包成 content 回填"不是礼貌,是协议逼的。**

## 第五部分:agent loop 全流程 —— LLM 只会吐字

把前面所有碎片串成一个完整循环。核心心法一句:

> **LLM 是个只会"吐字"的东西。它吐的字里可能夹着一张"我想调这些工具"的点单。是否吐这张单、单子长啥样,是 LLM 的事;但拿单子去后厨真炒菜、炒糊了怎么办、炒完再端回去问它还要不要加菜——全是你代码的事。**

### 1. 五步一轮,循环往复

一轮的五步:

1. **代码发起 LLM 调用**(messages + tools 一起发出去)。
2. **LLM 返回**,结果里可能带 `tool_calls`。注意:它返回的**不是"执行结果",是一张"点单"**——它自己没执行,只是开了张单子。
3. **代码解析、匹配工具名**。点了一个不存在的工具(幻觉)在这一步被抓住。
4. **拿名字 + 参数,真调函数**(`impls[name](**args)` 或转发给 MCP)。**这是整个 agent 里唯一"LLM 的意图变成真实动作"的地方**——这行之前一切是文字,之后文件真被写了。
5. **拿结果,包装成 role=tool 消息,回填进 messages**,进入下一轮。

### 2. 两个魔鬼细节

- **细节 A:这是循环,不是一次性。** 第 5 步把结果发回去后,LLM 看了结果**可能又要调下一个工具**(先搜索→再读文件→再总结),于是五步再来一遍。**什么时候停?** 看 LLM 这轮"还调不调工具":还调 → 继续;不调、直接吐文字答案 → 退出返回。**LLM 用"这轮还调不调工具"来告诉代码"我干完了没",这是整个 loop 的心脏。**
- **细节 B:工具失败不崩,是回填错误让 LLM 自救。** 工具报错不掀翻 agent,而是把错误当成工具的"返回结果"发回给 LLM,它下一轮就能自己改参数重试。**这就是 agent 比"写死的脚本"强的地方——它能读懂失败、自我纠正。**

### 3. 一张全景图

```
     ┌─────────────────────────────────────────────┐
     │  messages(system+skill清单+历史+query)       │
     │  tools(工具 schema,独立通道)                │
     └───────────────────┬─────────────────────────┘
                         ↓ 代码发起 (①)
                  ┌──────────────┐
        ┌────────→│     LLM       │  只吐字,从不碰工具
        │         └──────┬───────┘
        │                ↓ 返回 msg (②)
        │      msg.tool_calls 有货吗?
        │        ┌───────┴────────┐
        │       有                 无 → 直接吐了答案
        │        ↓                      ↓
        │  代码解析+匹配 (③)         判定收工
        │        ↓                      ↓
        │  真调函数 (**args) (④)     return answer ✓
        │  ← 唯一"意图变动作"的一行
        │  ← 失败?包成 {"error"} 不崩(细节B)
        │        ↓
        │  结果包成 role=tool 回填 (⑤)
        └────────┘  下一轮循环 (细节A)
```

去掉日志和注释,一个手写 agent 的核心就是这个循环。

## 第六部分:多工具的顺序与并发

如果 LLM 一次点了多个工具,并发还是串行?要保证顺序怎么办?

### 1. 数组顺序是建议,不是契约

- **典型的手写实现是串行**:用普通 for 遍历 `tool_calls` 数组,一个接一个执行,顺序 = LLM 给的数组顺序。
- **但这个顺序不可靠**:

> **`tool_calls` 数组的顺序是"建议",不是"契约"。LLM 可以乱序、可以把本该分步的工具并到一轮。for 循环只是忠实执行它给的顺序,不做任何纠正。**

两种情况:

- **有数据依赖(tool2 要用 tool1 的结果):** 大概率天然正确,但**不是靠数组顺序,是靠多轮循环**——tool2 的参数依赖 tool1 的输出,LLM 在还不知道结果时没法填 tool2 的参数,于是自然分两轮。这是 loop 结构"顺便"帮你保证的,但仍是概率行为。
- **无数据依赖、但业务要求顺序(如"先备份再删除"):** 真正的坑。LLM 可能把它们并进一轮、顺序还反了,for 循环忠实地按错误顺序执行 → 灾难。

### 2. 三档顺序保证方案

要保证顺序,回到那条铁律——**要确定性,下沉到代码**。按强度递增:

- **档 1:靠 prompt 提概率(弱)。** 在提示词里写"必须先 X 再 Y"。软的,提高倾向,拦不住尾部。
- **档 2:分轮 + 控制工具可见性(中)。** 不要一次把 tool1、tool2 都暴露;第一阶段只在 tools 里给 tool1,等它执行完,下一轮才把 tool2 放进去。LLM 想跳步都没那个工具可点。
- **档 3:代码 workflow 硬编排(强,生产主流)。** 干脆不让 LLM 决定顺序,顺序写死在代码里,LLM 只负责每一步内部的决策(填参数、判断内容),步骤之间的流转由代码控制。这就是各类图/链式编排框架(如 LangGraph)的核心价值。

**关于并发:** 手写实现通常串行。生产里若多个工具**互相无关**(如同时查三个数据源),会并发执行省时间。**但并发的前提正是"无顺序要求"。一旦要顺序,就退回串行 + 档 2/档 3。并发和顺序保证是对立的,别想兼得。**

## 第七部分:普通 tool 与 MCP 的归一

普通工具(本进程函数)和 MCP 工具(独立进程、走 MCP 协议)差别很大,但对 LLM 却是同一回事。这一节讲清"归一在哪、分流在哪"。

### 1. 对 LLM 归一,对执行分流

> **对 LLM:普通 tool 和 MCP 工具被合并进同一个 tools 列表,每一项都是同构的 `{"type":"function","function":{...}}`,没有任何字段标记"我是 MCP"。LLM 分不出、也不需要分。**
>
> **对代码:执行时才分流。靠一张"工具名 → 执行方式"的路由表——查本地实现表就是普通 tool(直接函数调),查 MCP 路由表就是 MCP 工具(走 client 跨进程转发)。**

分流点通常就是一个 `if`:名字在本地实现表里 → 本地调;否则在 MCP 路由表里 → 转发。

### 2. MCP 三步握手被折叠去哪了

MCP 协议核心是三步:**① 握手(initialize)② server 报告有哪些工具(tools/list)③ 真正调用(tools/call)**。普通 tool 没这些。既然最后都归一成 schema,这三步去哪了?

> **MCP 的三步握手并没有消失,也没有暴露给 LLM——它被"折叠"进了两个瞬间,发生在代码侧,LLM 完全看不见。**

- **折叠点一:生成 schema 时(对应握手 ① + 上报 ②)。** 代码为每个 MCP server 起一次连接:`initialize` 握手 → `tools/list` 问 server 有哪些工具 → 把 server 报上来的每个工具翻译成 OpenAI schema。**握手和上报,全折叠在"生成 schema"这一步里跑完了。**
- **折叠点二:执行工具时(对应调用 ③)。** LLM 点了某个 MCP 工具后,代码通过路由表找到对应的 client,再发起 `tools/call`。

**为什么路由表存的是 client 而不是 schema?** 因为执行③时要靠这个 client 去跟 server 通信。client 就是"这个工具怎么执行"的凭证。普通 tool 不需要凭证(直接查本地表拿函数),MCP tool 需要 client 当凭证——这就是为什么分流有两张表:本地表存函数,MCP 表存 client。

### 3. 两个殊途同归的翻译函数

归一的物理实现,是**两个几乎同构的翻译函数**,把两种来源不同的元数据压进同一个外壳:

| | 普通 tool | MCP tool |
|---|---|---|
| 元数据来源 | 反射 Python 函数签名 | 握手后 server 在 tools/list 里上报的 inputSchema |
| 翻译成 | `{"type":"function","function":{name,description,parameters}}` | 同左,同构 |
| 前置手续 | 无(函数就在本进程) | 需要先握手才能拿到 inputSchema |

> **两者"按同样方式归一到 schema",靠的就是这两个殊途同归的翻译函数。来源天差地别(反射 vs server 上报),终点被强行对齐成同一个 OpenAI 外壳。归一在 schema 层,分流在 dispatch 层——这是整个设计的骨架。**

## 第八部分:生产级怎么做

把手写实现放到 2026 年的行业坐标上,哪些是共识、哪些是学习级简化?

| 维度 | 手写学习版 | 生产级 | 判定 |
|---|---|---|---|
| 对 LLM 归一成一张工具表 | ✅ | ✅ | **完全一致,行业铁律** |
| schema 层归一、dispatch 层分流 | ✅ | ✅ | **完全一致** |
| MCP 连接生命周期 | 每次调用起/关 server | 长连接,连接池复用 | **学习级简化** |
| 工具数量管理 | 全量塞 | 检索 / 路由 / 分层 | **规模没逼到** |
| 工具治理(权限/审计/限流) | 雏形 | 重装 | **生产的大头** |

### 1. 归一思想是行业铁律

**"对 LLM 呈现一张无差别的工具清单,在代码侧分流执行"是所有严肃 agent 系统的共同骨架**,不是任何单个项目的巧思。Anthropic 的 Agent SDK、OpenAI 的 Assistants/Responses、LangChain 的 `BaseTool` 抽象,底层全是这套。

**为什么必然收敛到归一?** 因为**模型的接口只有一个 tools 参数**。你想让模型用任何能力,唯一入口就是把它翻译成一条 tool schema。所以归一不是设计选择,是被 API 形状**逼出来的唯一解**。任何"支持多种工具后端"的框架,底层必有一个归一层,无例外。

### 2. 生产绝不会一次性握手

这是手写版最明显的一处退化,值得单独敲:

- **手写版常见做法:每次调用 MCP 工具都完整地起子进程 → 建管道 → 握手 → 调用 → 关子进程。** 好处是同步封装简单、agent loop 碰不到 async,学习期心智成本极低。本质是拿"性能和连接效率"换"代码简单"。
- **生产做法:**
  - **连接复用/连接池:** server 在启动时握手一次,连接**保持存活**,后续所有调用复用同一 session。
  - **能力缓存:** tools/list 的结果握手后缓存,不每轮重问;MCP 还有 `tools/list_changed` 通知机制,让 server 主动告知工具变化,而非 client 反复轮询。
  - **长驻 server:** server 作为常驻服务(甚至独立部署成远程 HTTP/SSE server),而非每次现起现关的子进程。

> **归一思想生产照抄,但连接生命周期上,手写版是"一次性握手",生产是"握一次手复用整个会话"。MCP 协议本来就是为长连接会话设计的——每次重新握手,等于把协议为你省的手续自己又付了一遍。上生产第一件事就是改成长连接 + 连接池。**

### 3. 规模化:工具选择与治理

工具变多后,归一**之后**还要加两层:

- **工具选择(对抗 tool confusion):** 工具几十上百个时,模型在太多工具里选不准(经验值:一次给超过 20~30 个工具,准确率明显掉)。生产解法都在"归一之后再筛":**检索式**(按当前 query 向量检索出最相关的 N 个,只塞这几个)、**分层/路由**(先用便宜模型判断归哪类,再把那类工具给子 agent)、**命名空间分组**。skill 同理,多到几百就不能全塞 L1,得先检索。**这些都发生在归一之后——归一是地基,筛选是楼。**
- **工具治理(生产真正的大头):** 权限与鉴权(谁能调哪个工具)、审计日志(每次调用可追溯)、限流/配额/超时/重试、人在环(危险操作前人工确认)、沙箱与隔离(工具执行环境隔离)。手写版往往只有其中几颗"种子"(如简单的可见性门控、路径黑名单、调用日志、超时),生产是全套重装版。

**一个诚实的定位:**

> **手写的 agent,在"架构骨架"上和生产系统同构——归一层、分流层、tool calling 协议实现、失败回填、可见性门控、沙箱,这些关节都有。缺的不是"架构对不对",是"每个关节的工程成熟度":连接是一次性的(该池化)、工具是全量塞的(该检索)、治理是雏形的(该做完整权限审计限流)。**
>
> **好比搭出了一副骨架完整、比例正确的骨骼,生产系统是同一副骨骼长了肌肉、血管、免疫系统。不需要推倒重来,需要的是往每根骨头上长肉。而手写一遍骨架,是以后看任何 agent 框架都能秒懂"它在解决我手写时的哪个痛点"的唯一途径。**

## 附录:术语词典

| 术语 | 说明 |
|---|---|
| **tool(工具)** | 一个真能力(读文件、搜索、写盘)。LLM 调了代码就真执行,是"硬"的执行。 |
| **skill(技能)** | 一段建议/指南文字,注入进 LLM 注意力范围。读不读、听不听全凭 LLM 自觉,是"软"的。 |
| **function calling / tool use** | LLM 厂商定义的工具调用协议标准。前者 OpenAI 叫法,后者 Anthropic 叫法,结构同构。 |
| **tools 参数** | API 请求体里和 messages 平级的顶层字段,装工具的 schema。工具走这条独立通道,不在提示词里。 |
| **tool_calls** | LLM 返回里的字段。LLM 决定调工具时,以这个结构化数组表达"我要调哪些、参数是什么"。 |
| **tool_call_id** | 每个 tool_call 的唯一 id。回填结果时必须带上,LLM 靠它把"结果"和"当初点的哪一单"配对。 |
| **JSON Schema** | 描述参数结构的标准(type/properties/required)。tool schema 的 parameters 部分就是它。 |
| **schema 自动派生** | 从带类型标注 + docstring 的函数,用反射自动生成 tool schema,免得手写两份还怕对不上。 |
| **渐进披露(progressive disclosure)** | 先给 LLM 极简目录(L1),用到时再调工具拉出完整正文(L2)。省 token 的策略。 |
| **prompt caching** | 服务端缓存固定的 prompt 前缀,命中后 token 成本大幅降低。决定"全量注入 vs 渐进披露"的关键变量。 |
| **agent loop** | "发 LLM → 看它点不点工具 → 点了就执行并回填 → 再发"的循环,直到 LLM 不再点工具、直接给答案。 |
| **归一(normalization)** | 把不同来源的工具(本地函数、MCP)翻译成同构的 tool schema,让 LLM 无差别看待。 |
| **分流(dispatch)** | 执行时按工具名路由到不同执行路径(本地函数调 vs MCP 转发)。 |
| **MCP(Model Context Protocol)** | 工具/能力以独立进程/服务对外提供的协议。核心三步:握手 initialize → 上报 tools/list → 调用 tools/call。 |
| **tool confusion** | 工具太多时 LLM 选不准的现象。经验阈值约 20~30 个,超了准确率明显下降。 |
| **软 / 硬** | 本文主线。软 = LLM 决定的概率行为;硬 = 代码/协议保证的确定行为。要把软的变确定,就下沉到代码。 |

## 附录:一页速查

**主线(记住这一条,其余都是展开):**
> 任何一件事都问"软还是硬"。软 = LLM 决定(概率);硬 = 代码/协议保证(确定)。要确定性,就把它从 LLM 手里拿走,下沉到代码。

**skill vs tool:**
> tool 是硬能力(调了真执行),skill 是软建议(读不读全凭自觉)。skill 不是 SOP,是便利贴。错了会出事的别交给 skill,下沉到代码。

**渐进披露:**
> 全量注入拿 token 换 round-trip,渐进披露拿 round-trip 换 token。有 caching → 可全量;没 caching → 必须渐进披露省 token。

**tool calling 协议:**
> 去程走 tools 参数(独立通道,非提示词),schema 外壳是协议、内容从函数反射派生。回程 LLM 用 tool_calls 表达调用意愿——"要调就必须用这格式"是硬的,"调不调"是软的。回填三件套 role/tool_call_id/content 是硬约定,连失败都必须回填。

**agent loop:**
> LLM 只会吐字,可能夹一张工具点单。是否点单、单子长啥样是 LLM 的事;执行、纠错、再问全是代码的事。用"这轮还点不点工具"判断收工。工具失败不崩,包成错误回填让它自救。

**多工具顺序:**
> 数组顺序是建议不是契约。要保证顺序:档1 prompt(弱)、档2 分轮控制工具可见性(中)、档3 代码硬编排(强)。并发和顺序保证对立。

**普通 tool vs MCP:**
> 对 LLM 归一成一张表(分不出谁是 MCP),对代码分流执行(两张表:本地存函数、MCP 存 client)。MCP 三步握手折叠进"生成 schema"和"执行工具"两个瞬间,LLM 看不见。归一在 schema 层,分流在 dispatch 层。

**生产坐标:**
> 归一思想是行业铁律(被 API 形状逼出的唯一解),手写版骨架与生产同构。真正差距在工程成熟度:连接该池化(别一次性握手)、工具该检索(别全量塞)、治理该完整(权限/审计/限流/人在环)。骨架对了,往上长肉即可。
