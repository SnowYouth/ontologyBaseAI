## 1. 问题是什么，为什么重要

### 1.1 结构化知识是准确率的最大杠杆，也是最贵的人力黑洞

让 LLM 查企业数据库（text-to-SQL）时，准确率的头号杠杆不是换模型，是**给它一层人工维护的语义知识**。有一组被反复引用的实证数字：

| 做法 | 准确率 |
|---|---|
| 裸表 schema 直接 text-to-SQL | 16% |
| 映射成知识图谱后查询 | 54% |
| 加本体校验纠错回路（OBQC） | 72% |

（来源：Sequeda & Allemang 等，data.world AI Lab，arXiv:2311.07509 / 2405.11706）

问题在于，那层语义知识是**人一条一条写出来的**：这张表是什么、这个字段什么含义、这两张表怎么关联、查这类问题默认要加哪个过滤条件、这个状态码 `300001` 是什么意思。

于是出现一对矛盾：

- **知识越全，AI 越准** —— 这是杠杆；
- **知识全靠人写，业务天天变** —— 这是黑洞。

一份 2026 年的知识图谱构建综述（arXiv:2510.20345）给出的警告很直接：**没有自动化，本体会变成 dead model，跟不上业务。** 建好那天就是最新的一天，之后一路衰减。

### 1.2 于是所有人都想到同一件事

「能不能让 AI 自己维护这层知识？」

这就是本文的主题。但在动手之前，必须先分清一件事：**「自进化」这个词现在指三件完全不同的事**，混为一谈会让你抄错方案。

## 2. 「自进化」的三支：一张认知地图

2026 年至少有四份综述在梳理这个领域，各自的切法不同。其中最新的一份（arXiv:2607.13104）明确批评前作「把基础模型微调和 agent 脚手架当成孤立话题，缺乏统一视角」，它给出的切法最锋利：

> **唯一的硬边界是：要不要动模型权重。**

按这条线加上「知识形态」这个维度，可以切出三支：

```
                        自进化 (Self-Evolving AI)
                                 │
        ┌────────────────────────┼────────────────────────┐
        │                        │                        │
   ① 模型自训练              ② 脚手架自改进           ③ 知识资产演化
   (改权重)                  (不改权重)               (不改权重)
        │                        │                        │
  SFT / RL / self-play      prompt / memory /        本体 / KG /
  ExSPIN, ReEx-SQL          tool / workflow          语义层 / schema
        │                        │                        │
   需要训练基础设施          生态最繁荣、坑最清楚      文献与代码都最薄
   多数团队不具备            可直接借失败经验          ← 本文重点
```

### ① 模型自训练：改权重

用执行结果或自我对弈产生的信号去更新模型参数。text-to-SQL 领域的代表是 ExSPIN（把 SQL 执行结果喂回参数更新）、ReEx-SQL（execution-aware 强化学习）。

**特点**：效果上限高，但需要训练基础设施、标注流程和算力。对绝大多数应用团队而言不是选项。

### ② 脚手架自改进：改 prompt / 记忆 / 工具 / 工作流

不动权重，改模型周围的一切。这是**目前生态最繁荣的一支**：GitHub 上搜 `self-evolving agent` 有 1,539 个仓库，头部项目 46.7k / 34.8k / 14.1k stars，且大多在持续更新。

它也是**失败模式被研究得最透的一支** —— 有多个专门的 benchmark（EvoMemBench、Evo-Memory、LifelongAgentBench）在系统性地量化「什么不work」。第 6 节会详细讲，因为这些坑对第③支有直接的移植价值。

### ③ 知识资产演化：让结构化知识自己长

让本体、知识图谱、语义层元数据这类**结构化、有 schema、可校验**的知识资产自动扩充和维护。

**这一支的现状很特殊：文献和代码都极薄。**

一个粗糙但方向一致的观察 —— 同样用 GitHub API 按 stars 排序搜索：

| 搜索词 | 仓库数 | 头部 stars |
|---|---|---|
| `self-evolving agent` | 1,539 | 46.7k / 34.8k / 14.1k / 12.6k |
| `ontology evolution LLM` | 3 | 1 / 1 / 0 |
| `knowledge graph curation human in the loop` | 1 | 0 |
| `semantic layer text-to-sql feedback` | 2 | 1 / 0 |

> ⚠️ **这个对比要打折看**：关键词搜 GitHub 很粗，本体工程领域大量活跃项目挂在 Protégé、LinkML、OWL、生信 curation 工具链等名下，不会被这几个词命中。所以「零生态」是过度解读。
>
> 但**换四种问法结果一致**，且与论文侧的观察吻合 —— 论文侧的原话是：「从失败更新语义模型」这件事**工程博客讲得多，论文覆盖极薄**，绝大多数论文优化的是生成器（prompt / agent / 权重），**不优化它所读的那层 schema 元数据**。最接近的形式化工作是 Reflective Reasoning for SQL Generation（arXiv:2601.06678）。

**结论**：做第③支，你处在一片相对空白的地带。好处是有价值，坏处是**没有现成的坑图可抄**，必须保守设计，并主动从第②支借失败经验。

### 2.1 三支的选择建议

| 你的处境 | 建议 |
|---|---|
| 有训练基础设施 + 有标注数据 | ① 可以考虑，但先做②③ 性价比更高 |
| 想让 agent 干活越来越熟练 | ② 生态成熟，直接选框架 |
| 有一份人工维护的结构化知识资产在拖后腿 | ③ 本文重点 |
| 不确定 | 先做③的「反馈信号采集」—— 它是①②③ 的共同前置 |

## 3. 知识飞轮的真实形态

### 3.1 教科书版本

「知识飞轮」的标准叙事是一个闭环：

```
用真实使用产生信号 → 从信号里提炼知识 → 知识回写进系统
       ↑                                        │
       └────────── 系统变好，产生更多使用 ←───────┘
```

学术上有一个对应的结构叫 **RAC 飞轮**（Reason → Align → Construct），出自 arXiv:2604.08603（*From Business Events to Auditable Decisions*，2026-04）。它要解决的正是本体冷启动问题：从真实部署交互中捕获候选本体节点，路由到治理审核流程，让企业本体从实际使用中增量生长，而不需要预先完整规约。

> ⚠️ **重要限定**：RAC 在该论文中**是 future work，写在附录 A.8，没有部署过**。论文自陈当前实现跑在「节点和场景条件全部预先指定的合成 Neo4j 本体」上，RAC 被列在「future work: RAC governance hardening」。
>
> 引用它时请把它当作**同向的设计构想**，而不是「业界已跑通的成熟范式」。

### 3.2 生产版本：闭环其实是开环

去看真实系统，会发现一个一致的模式：**没有人真的让环自动闭合。**

| 系统 | 宣称 | 实际 |
|---|---|---|
| **NVIDIA data-flywheel**（开源，215★，Apache-2.0） | 「闭环飞轮」 | **开环**：评估自动化、promotion 全人工、无自动门。项目自陈定位是 "flashlight not autopilot"。**且已 deprecated** |
| **NVIDIA NVInfo / MAPE**（arXiv:2510.27051，同行评审） | MAPE 控制回路 | 3 个月只采集 **495 条负样本** → LLM-judge 筛出 140 疑似 → **专家确认 32 条真错** → 凑成 685 条 ground truth。人在关键环 |
| **Airbnb AITL**（arXiv:2510.06674，EMNLP 2025 Industry） | Agent-in-the-Loop 数据飞轮 | 四类标注全部由真人客服在工作流中产生。效果：重训周期从数月缩到数周，retrieval recall@75 +11.7%、precision@8 +14.8% |
| **OpenViking**（34.8k★，topic 挂 `self-evolving`） | 「Self-evolving Context Database」 | 代码里只有**异步抽取写入 + 分层检索**，**无准入校验 / 冲突解决 / 淘汰 / 审批状态**。核心机制在未开源的论文里 |
| **vanna-v3**（1★，几乎无人知） | feedback loop + eval gate | **属实**。是本次调研中营销与代码最一致的一个（详见 §4.5） |

**两条经验**：

1. **stars 数与可抄性可能负相关。** 34.8k stars 那个 "self-evolving" 名不副实；1 star 那个把状态机和回归门都实打实写了。评估开源项目要读代码，不能读 README。
2. **「全自动闭环」在 2026 年仍不是生产实践。** 所有严肃系统都把人放在准入环节。这不是技术不够，是**信任模型的选择**。

### 3.3 修正后的飞轮

把生产观察折进去，真实可行的飞轮长这样：

```
   ① 信号采集 ──→ ② 提议生成 ──→ ③ 自动校验(多道) ──→ ④ 人工审批 ──→ ⑤ 写入
        ↑                                  │                              │
        │                                  ↓ 未过                          │
        │                          ⑥ 负样本留存 ←───────────────────────────┘
        │                                                                  │
        └──────────────────── 系统变好，产生新信号 ←────────────────────────┘
```

关键在于 ③ 和 ④ 的分工：**自动校验不是为了替代人，是为了把人的工作从「判对错」降级成「判要不要」。** 这是整个设计的核心命题 —— 也是决定飞轮会不会被审核瓶颈压垮的地方。

## 4. 飞轮的六个部件

### 4.1 信号采集：只取失败，还是成功也取？

这是设计飞轮时第一个要拍的架构选择题，而且有明确答案。

**结论：失败驱动知识变更，成功走旁路不碰知识库。**

**理由一：「成功即正确」的地基是虚的。**

在真实业务库基准 BIRD 上，SOTA 执行准确率停在 **77–82%** —— 即约每 5 条就有 1 条「跑得通、看着合理、但答错」。更要命的是错误构成：一份 4,602 条错误的分析显示 **81.2% 是 schema/语义错，只有 18.8% 是语法错**（Shen et al. 2025）。语法错会报错，语义错**不会** —— 它安静地返回一个错误答案。

这类错误有个专门的名字：**silent plausible error（静默合理错误）**。而生产环境里你没有 ground truth 对账，只有「用户没抱怨」这一个信号 —— 但用户往往分不清对错，这正是静默错误的定义。

所以「跑通了 + 没人抱怨 = 正确」这个推理链是断的。方案 B（成功也回写知识库）会把概率性的巧合焊进规则源，污染下游所有查询。

**理由二：业界成熟飞轮的知识级变更几乎都由失败驱动。**

- NVIDIA NVInfo：3 个月**只采 495 条负样本**，论文明说用户几乎只报负反馈、不验证正确结果 —— 燃料天然偏失败。
- Airbnb AITL：四类标注中，**采纳/偏好标注可以延迟标，唯独「缺失知识」要求立即标** —— 成功信号松、失败信号紧。且成功侧产出的是正负样本对喂检索/排序模型，**不直接改知识库**。该系统还有个 VJ 过滤器剔掉 14–34% 的低质标注 —— 即便是人工标的成功信号，也要重过滤才敢用。
- DDC 方法论（arXiv:2603.14057）：明确「用 agent 失败作为主信号」，并用了 **TDD 的类比** —— 先失败，再补知识。

**理由三：吞吐。** 失败量天然有限（NVIDIA：3 个月 495 条），成功量是全流量，可轻易高一到两个数量级。审核端撑不住（见 §4.4）。

**成功信号去哪：三条旁路，都不改知识库**

| 旁路 | 做什么 | 业界依据 |
|---|---|---|
| golden query 库 | 验证过的「问题–SQL」对存进向量库做 dynamic few-shot | OpenSearch-SQL 等，业界标准做法 |
| 使用频次统计 | 哪些实体/关系高频被用，供人工优先审查和优化 | 通用运营实践 |
| 不落规则 | 成功不产生知识变更 | 本节理由一 |

### 4.2 提议生成：证据锚定

让 LLM 提议「应该补一条什么知识」时，**强制它附带可核对的证据和推理轨迹**，而不是只给结论。

有同行评审背书的实证：**GOFlowLLM**（Oxford Bioinformatics 2026）让模型走基因本体 curation 的标准流程图并输出 reasoning trace 后，curator 认同 **95% 的推理步骤、90% 的证据选择**，58 小时产出 2,538 条候选。

机制上这做了两件事：
1. **源头减量** —— 拿不出证据的提议根本不该进队列；
2. **加速审核** —— 人读证据比自己重新查快得多。

> ⚠️ 常见的三个流传数字 —— 「48,403 提议 vs 775 人工决定的 60:1 积压」「证据锚定使角色赋值从 36 条压到 4 条」「审核从 4 分钟/条降到 1 分钟/条」—— 本次调研**未能在同行评审主源核实**。方向性判断（生成侧可 scale、审核侧不可 scale）是常识性的，但**这三个具体数字不应被当作证据引用**。详见附录 C。

### 4.3 自动校验：静态校验 vs 执行式验证

这是本文技术含量最高的一节，也是最容易做错的一节。

#### 4.3.1 两类校验的效果差距是实证的

| 类型 | 做法 | 实测贡献 |
|---|---|---|
| **静态 / intrinsic 自检** | 不执行，只重读自己的产出找问题 | DIN-SQL 的 self-correction 消融**仅 1–3 个百分点**，且喂 generic buggy prompt 时**反而掉分** |
| **执行式验证** | 真跑，看报错、看空结果集，再改写 | MAC-SQL 的 Refiner 消融 **+4.63**（BIRD dev），是其三个 agent 中贡献最大的 |

**结论：不执行的自我检查，效果接近于无。** 任何以「让 LLM 自己再看一遍」为核心的准入设计，都要预期到这个天花板。

> 有一个重要的例外值得说明：如果静态校验器手里握着**模型不知道的外部真相**（比如一份人工维护的本体，记录着哪些表之间真的存在关联），那它就不是 intrinsic 自检 —— 它是拿外部知识做确定性证伪，价值远高于 1–3 个百分点。
>
> 但它仍然只能判「本体说这条不成立」，**判不了「本体没记载的东西在真实数据里成不成立」**。后者只有执行才知道。这个区分决定了两类校验器的岗位分工（见 §7.3）。

#### 4.3.2 「探针」不用自己发明：这是有 30 年沉淀的老问题

如果你想验证「A 表的某列是否真的能关联到 B 表」，最朴素的做法是打一条探针 SQL：

```sql
SELECT COUNT(*) FROM a JOIN b ON a.X = b.Y LIMIT 1   -- 非空就算成立？
```

**这个判据是错的，而且错法早有定论。** 这个问题在数据剖析（data profiling）领域叫 **inclusion dependency (IND) 发现 / 外键发现**，有 30 年研究沉淀：

- 经典算法：**SPIDER**（sort-merge）、**BINDER**（hash 分区，支持 unary + n-ary，比 SPIDER 快约 26×）
- 现成实现：**Metanome**、**Desbordante**
- 核心结论：**光靠「值包含 / 跑通且非空」判外键会产生大量假阳性**，必须叠加基数、随机性等量化特征。

典型反例：**两个自增主键必然能 JOIN 上，但语义完全无关**。TPC 类基准里的小整数代理键因为值域窄，也必然广泛重叠。

#### 4.3.3 可直接抄的三层探针判据

综合 DBAutoDoc（arXiv:2603.23050）的 G1–G8 硬门 + Freyja（arXiv:2412.06637）的 join quality + Scalable Join Inference（arXiv:2603.04176）的 ML 特征定义：

**第一层 · 硬门（确定性，先滤）**

| 门 | 判据 | 挡住什么 |
|---|---|---|
| G1 | target 列必须 PK-eligible（唯一、非空、非空白） | 无方向的伪关联 |
| G4 | `distinct(source.col) / distinct(target.pk) ≤ 1` | 违反多对一的候选 |
| G8 | **跳过 source 本身就是 PK 的候选** | ★两个自增 PK 的巧合重叠 |
| — | source/target 任一为空表 → 判 UNKNOWN，不判通过 | 空表让「非空」判据失去意义 |

**第二层 · 量化阈值**

- **值包含率 ≥ 0.75**：`|distinct(source) ∩ distinct(target)| / |distinct(source)|`（DBAutoDoc 的 G6，留 25% 容脏数据）
- **multiset Jaccard × 基数比例**（Freyja 的 join quality）：兼顾重叠度和基数，假阳性低于单一 Jaccard
- **随机性 / 选择性特征**（Rostin 2009 的十特征谱系）：区分「语义相关」和「值域巧合重叠」

**第三层 · 加权评分**（DBAutoDoc 权重，可作起点）

```
值重叠 40% + 命名相似 20% + 基数比 15% + target-is-PK 15% + null 处理 10%
```

命名相似（编辑距离、`_ID` / `_KEY` 后缀）是**廉价且强的信号**，别因为「不够严谨」而不用。

> ⚠️ 阈值 0.75 和上述权重是 DBAutoDoc 一家的实验值，**未见跨数据集独立复现**。落地时当起点，用你自己的真库校准。
>
> 另注：inclusion coefficient 的经典严格定义是**全量包含**，带阈值的叫 partial IND（见 SPIND / pSPIDER）。0.75 是工程放宽，别混淆。

#### 4.3.4 探针的陷阱清单

| 陷阱 | 后果 | 对策 |
|---|---|---|
| 巧合匹配 | 两个自增 PK 必能 JOIN，语义无关 | G8 + 基数比 + 随机性特征 |
| 空表 | 「非空」判据失去意义 | 硬门先查行数，空表判 UNKNOWN |
| NULL 语义 | `NULL != NULL`，含 NULL 列会漏 | 包含率分母基于 distinct **非空**值 |
| `LIMIT 1` 当代表 | 只证「至少一行连得上」，**不证包含率** | 包含率必须全量或大样本估 |
| 数据倾斜 | 少数热键掩盖整体不匹配 | 看分布，不只看总数 |
| 跨库 | 成本显著更高（BINDER 在 DB 输入上比文件慢近一倍） | 分段执行，考虑只读副本 |

#### 4.3.5 探针的安全：AST 强制只读

往生产库打探针，必须保证只读。成熟做法是**分层防御**（不是一堵厚墙，是洋葱多层）：

1. **AST 层**：`sqlglot.parse_one` → 断言根节点是 `Select` / `Union` → `.find_all()` **遍历全树**（含 CTE 和子查询）拒绝任何 DML/DDL 节点
2. **注入 LIMIT 在 AST 层**（`set_limit`），**不要字符串拼接**
3. **解析失败要响亮失败**，回落关键字黑名单（DROP/TRUNCATE/ALTER…），**绝不静默放行**
4. **DB 侧硬底线**：只读角色 + 语句超时（注意 MySQL 的只读是 per-call 而非 per-connection，每次调用都要设）

已知的绕过方式：前缀检查会放过 `PRAGMA journal_mode`、CTE 里藏 INSERT、`INTO OUTFILE`。**sqlglot 能解析 ≠ sqlglot 会拒绝** —— 它本身不拒 DML，白名单要自己写。

### 4.4 人工审批：审核经济学

飞轮的真正瓶颈在这里。**生成侧可以 scale，审核侧不能。**

**分流三分法**（业界共识，但主要来自实践博客而非同行评审）：

| 置信度 | 处理 | 抽检 |
|---|---|---|
| 高 | 自动应用 | 1–5% 抽检 |
| 中 | 进人工队列 | 全审 |
| 低 | 自动拒 / 降级 | — |

关键细节：**阈值应按动作类型分层，而不是全局一个数**。低影响、可逆的变更放宽自动应用；高影响、不可逆的硬门控。队列拥塞时可自适应放宽中段阈值，但**绝不自动放行低置信项**。

**队列的度量指标**：

- override 频率（人推翻自动决策的比例）
- 队列深度（作为**一级运营告警信号**，不是次要指标）
- 审核周转时间
- 每人工小时带来的系统改进量
- 自动接受项的抽检合格率
- knowledge freshness（知识新鲜度）

**修正传播（最关键的一条）**：一次人工修正应当能变成规则，防止同类提议反复进队列。做法有两种：

1. override 时**强制留一句备注** → 回流训练集 / few-shot（Airbnb AITL、MIBiG 4.0 的 active learning 回路）
2. **相似规则传播** —— 用户标错一条，系统按相似度找出同类可疑项一并复核（实体匹配领域的成熟机制，arXiv:2003.13114）

没有这一条，审核队列会随知识库规模**线性增长**；有了它，人工审核才能摊薄。

### 4.5 写入：双状态机 + fail-closed 回归门

这三个设计来自 vanna-v3 的实际代码（本次调研中营销与实现最一致的项目），可直接抄进 Python + SQLite 项目：

**① 双状态机分离**

```sql
review_status  ∈ {NULL, pending, approved, rejected}   -- SQL CHECK 硬约束
patch_status   ∈ {applied, failed}                      -- 写入成败单独记
```

审批状态和写入状态**必须分开**。"人批准了" 和 "真的成功写进去了" 是两件事，合并会产生半吊子状态。配套字段：`reviewer_id` / `reviewer_note` / `reviewed_at` / `created_at` / 内容 `hash` / `reason_codes_json`（来源证据）。

**② fail-closed 回归门**

变更落地前跑评估集，**任一指标低于 baseline 即拒**：

```python
passed = not reasons          # 任一 reason 即失败 —— fail closed
```

检查项：
- 评估集的 **sha256 + case_count** 基线与候选一致 —— **防偷换评估集**（这个细节很关键，否则「回归门」可以被绕过）
- 每项质量指标 ∈ [0,1]
- 任一指标低于 baseline → `aggregate_regression`
- 分片级检查 → `slice_regression`（防止整体不降但某一类塌了）
- 可设 `minimum_improvement` 门槛（不只是不退步，还要有进步）

**③ 审批查询守卫**

```sql
WHERE review_status = 'approved' AND patch_status = 'applied'
```

**只有「已批准且已成功落库」才算数** —— 杜绝半吊子提议污染下游。

**三个项目的共同模式**：反馈**从不直接改知识库本身**，先落**独立表**，经评估 + 人审才提升。这是最值得记住的一条架构纪律。

### 4.6 负样本留存

探索失败的提议**要留存**，不要丢。存成「负知识」记录：试过的死路 + 失败分类 + 边界条件。

三个用途：
1. **防止反复探索同一条死路**（省算力，也省审核）
2. **作为待审提议的去重键**
3. 人工可查 —— 「这条为什么没做」是有价值的组织记忆

学术上对应「负结果资产化」的思路（arXiv:2606.21024 / 2606.26859）。

## 5. 生产环境真实选型

| 维度 | 现实 |
|---|---|
| **自动化程度** | 无人做全自动闭环。所有严肃系统都把人放在准入环节 |
| **人的位置** | 统一在「批准候选」这一环 |
| **人的工作性质** | 从「判对错」降级为「判要不要」—— 靠证据锚定 + 自动校验实现 |
| **信号来源** | 失败为主。NVIDIA 3 个月 495 条负样本 |
| **重训/更新周期** | Airbnb：从数月压缩到数周（这已是被当作成果报道的改进） |
| **知识写入路径** | 从不直接改，先落独立表 → 评估 → 人审 → 提升 |
| **回归保护** | fail-closed，任一指标退步即拒；评估集用 hash 钉死 |
| **成本控制** | 探针走只读副本 + 超时 + 采样；AST 层强制只读 |

**如果你在做选型，一句话总结**：不要按 stars 选，按「有没有状态机和回归门」选。

## 6. 已知失败模式：哪些会落到你头上

第②支（agent memory）在「知识单元自动积累并被检索复用」这件事上已经踩了几年坑，有严谨 benchmark 量化。第③支和它**结构同构**，所以这些坑有直接的移植价值 —— 但需要逐条判断，不能照搬。

### 6.1 会重现的坑

**① 错误传播 / experience-following（最危险）**

严谨实证（arXiv:2505.16067）：输入相似度高 → 输出高度相似。**被检索到的坏条目会污染新的执行**，若结果又回存，错误以复利方式传播。自动驾驶案例：selective 策略 51% vs unbounded 32%。

**为什么会重现**：结构化知识同样是「提议 → 入库 → 未来被检索复用」的闭环。坏条目一样是承重的。

**唯一的防线是准入校验 + 回归测试** —— 但同一篇论文的原话是：**「即便有人工审查，错误条目仍不可避免。」** 所以回归门是必须的，不是可选的。

**② 跨环境负迁移**

EvoMemBench 实证：决策步骤不同的环境之间迁移会变成负收益。

**在知识资产上的表现**：一条关联路径在 A 库成立，被复用到语义不同的 B 库 → 安静答错。多数据源场景必须让知识条目带上数据源归属。

**③ 检索多样性坍缩（条件性重现）**

论文实证（arXiv:2604.27003）：存得越细，同质查询越是漏斗式命中同几条近邻，「池子看着丰富、召回极度重复」。

**是否重现取决于你的知识怎么被消费**：
- 如果知识通过**相似度检索**喂给 LLM → **会重现**。结构化和唯一键救不了检索层。
- 如果知识**全量枚举**塞进 prompt → **当前免疫**，但见 §6.3 的延迟坑。

### 6.2 结构化知识天然免疫的坑

| 坑 | 为什么免疫 |
|---|---|
| 自由文本记忆不耐老、难审计、互相矛盾 | 结构化 + 唯一键 + 可用约束（SHACL / disjoint / 自定义校验器）**确定性检出**矛盾，不靠 LLM 自觉 |
| 压缩丢细节 | 不做摘要压缩，条目是离散断言，无信息损耗式老化 |
| 长程退化三阶段（细节丢失 → 目标漂移 → 灾难性遗忘） | 那是长上下文/自由文本记忆的退化曲线；外部持久化结构库无上下文窗口约束 |

**这是结构化知识相对 agent memory 的核心结构优势**，值得在设计时刻意保住 —— 一旦往知识条目里塞自由文本大段描述，这个优势就开始流失。

### 6.3 一个容易被忽略的延迟坑：目录膨胀

如果你的知识目录是**全量塞进 system prompt**（而非检索），你当前免疫「检索多样性坍缩」。但你换来了另一个问题：

**目录长度随知识库线性增长，全部压在上下文里。**

自演化一旦跑起来，知识持续增长 → 目录无限膨胀 → 撞上下文窗口上限。到那天你**必须**引入选择性召回 —— 而**引入的那一刻，§6.1 的第③条坑就出现了**。

**设计建议**：在引入选择性召回的同时就要引入多样性约束（MMR 或分层检索），不要等到坍缩发生。这个坑是「现在免疫、演化后必然遭遇」的类型，值得提前记在路线图里。

### 6.4 可直接借用的缓解手段

| 手段 | 来源 | 怎么用 |
|---|---|---|
| **蒸馏失败而非原样记录** | Reflexion / ExpeL / AWM，实证有效 | 不存原始失败 SQL，提炼成可复用的规则/断言 |
| **evaluator-driven admission** | arXiv:2505.16067 实证 | 准入前跑评估集（对应 §4.5 的回归门） |
| **history-based deletion** | 同上 | 定期回归，淘汰失效条目 |
| **访问频次淘汰** | forgetting 文献，selective > unbounded | 久不被召回的条目降权或标记待审 |
| **periodic consolidation** | 同上 | 定期去重 + 合并冲突 |
| **versioned records + 时间戳** | KG staleness 文献 | 覆盖旧值而非并存，治陈旧 |
| **write-path 去重 / canonicalization** | 通用 | 入库前查唯一键去重 + 冲突检测 |

**最容易漏的一条：淘汰机制。** 大多数设计只想「怎么加」，不想「怎么减」。**别只增不汰。**

> ⚠️ 关于知识图谱自身的退化（KG decay / ontology bloat），目前**缺少 EvoMemBench 级别的严谨对照实验**。综述明确指出「自动大规模增长会引入矛盾、破坏推理」「无 stewardship 必然衰退」，但多为定性论断。移植这些结论时，实证强度弱于 §6.1 的前两条。
>
> 另一个未知数是**规模阈值**：agent memory 的坍缩在数千条量级显现，结构化知识在什么量级触发无数据，需要自建小 benchmark 观测。

## 7. 本项目当前怎么做的

> 本节是 ontologyBaseAI 项目的自我对照。其余章节是通用知识，本节可跳过。

### 7.1 已有的部件

| 飞轮部件 | 现状 | 评级 |
|---|---|---|
| **知识资产本体** | SQLite 四表（entity / relation / concept / filter_rule）+ enum_value，行级可编辑，8 域 / 数十实体 / 92 活边 | ⭐⭐⭐⭐ 地基扎实 |
| **确定性校验器** | `validate_concept`（5 类检查）/ `validate_filter_rule`，纯函数 + 真库 I/O 注入 | ⭐⭐⭐⭐ 心智已成熟 |
| **静态 SQL 校验（OBQC）** | sqlglot 解析 + 4 类校验（JOIN 硬 / 列归属硬 / 枚举软 / filter_rule 软）+ 熔断 + 强制上浮 | ⭐⭐⭐⭐ 已接入执行链路 |
| **CQ 回归基建** | `cq_runner` + 验证回路 B（改本体 → 一键重跑 CQ → 人工三档打分 → 上轮对比） | ⭐⭐⭐⭐ **回归门的地基已在** |
| **前端人审界面** | 4 Tab 编辑器 + 一键校验红绿灯 | ⭐⭐⭐ 有界面，但无提议队列 |
| **可观测性** | 全链路 JSONL 埋点（硬约定） | ⭐⭐⭐⭐ 信号采集的前置已就绪 |
| **执行式验证 / 真库探针** | **完全没有** | ⭐ 最大缺口 |
| **提议队列 + 双状态机** | **完全没有** | ⭐ 缺口 |
| **负样本留存** | **完全没有** | ⭐ 缺口 |
| **淘汰机制** | 只有 `valid` 标记 + 软删，**无频次淘汰 / 整合 / TTL** | ⭐⭐ 只增不汰 |

### 7.2 已查证的两条事实

**① 本体目录是全量枚举，不是检索。**

`core/ontology.py:459` 的 `build_catalog_text` 把所有实体 + 所有 `valid==1` 概念无条件拼进 system prompt，无 embedding、无 top-k、无相似度。

→ **§6.1 的「检索多样性坍缩」当前不适用**，但 **§6.3 的目录膨胀延迟坑成立且必然到来**。

**② RAG 侧是纯 top-k，无多样性约束。**

`rag/retriever.py:280`：向量 + BM25 + RRF 融合 + cross-encoder 精排，全程按分数排序取前 N，无 MMR / diversity 机制。

→ 但该链路服务的是 `corpus/` 文档问答，**与本体自演化主线不相干**。记录在案，不是本轮的债。

### 7.3 一处需要纠正的既有判断

项目内部曾有两个互相冲突的说法：OBQC 是「准入闸门」还是「回归测试器」。现在有证据可以定论：

**OBQC 应当是回归门，不是准入闸门。** 两条独立证据：

1. OBQC 是纯静态解析（不碰库），属于 §4.3.1 里 intrinsic 自检那一类的机制族。虽然它握有本体这份外部真相（所以远强于 DIN-SQL 的 1–3 点），但它**判不了「本体没记载的关联在真实数据里成不成立」** —— 而这恰恰是自演化提议要判的东西。
2. 方向相反：OBQC 的逻辑是「本体没有这条边 → violation」，而自演化探索出的新路**本来就不在本体里** —— 用它当准入闸门会把合法的新发现全部误杀。

**正确的分工**：
- **准入闸门 = 真库探针**（执行式，判「这条提议对应真实数据吗」）
- **回归门 = OBQC + CQ 全量重跑**（判「加了这条，原来对的还对吗」）

两个都要，岗位不能混。

### 7.4 与生产的差距总结

| 差距 | 严重度 |
|---|---|
| 无执行式验证 —— 准入闸门整个缺失 | 🔴 阻塞自演化 |
| 无提议队列 / 状态机 —— 人审无载体 | 🔴 阻塞自演化 |
| 无负样本留存 —— 会反复探索死路 | 🟡 影响效率 |
| 回归门未 fail-closed 化 —— CQ 基建在，但没接成「退步即拒」的自动门 | 🟡 地基在，接线未做 |
| 只增不汰 —— 无淘汰/整合机制 | 🟡 长期腐化风险 |
| 目录全量枚举 —— 演化后必撞上下文上限 | 🟡 延迟坑 |

## 8. 补齐路线（按 ROI 排序）

这是通用建议，任何做知识资产演化的项目都适用。

### 第 1 优先：真库探针（准入闸门）

**为什么第一**：它是唯一能判「提议是否对应真实数据」的机制，且证据显示执行式验证的效果显著高于静态自检。没有它，整个飞轮没有准入关。

**怎么做**：
- 直接采用 §4.3.3 的三层判据（硬门 → 量化阈值 → 加权分），**不要自己拍 `COUNT>0`**
- 阈值用自己的真库校准，不要照抄论文数字
- 安全走 §4.3.5 的 AST 分层防御
- 借鉴 IND 发现的成熟算法（SPIDER / BINDER），必要时直接用 Metanome / Desbordante

### 第 2 优先：提议队列 + 双状态机

**为什么第二**：人审需要载体。没有队列，提议无处可去。

**怎么做**：抄 §4.5 的 `review_status` + `patch_status` 双状态机，SQL CHECK 硬约束，配 `reason_codes_json` 存证据。查询一律用审批守卫。

### 第 3 优先：fail-closed 回归门

**为什么第三**：防止新知识把老能力搞坏。如果已有 CQ 评估基建，这一步是接线而非发明。

**怎么做**：任一指标低于 baseline 即拒；评估集 sha256 钉死防偷换；加分片级检查。

### 第 4 优先：负样本留存

**为什么**：便宜，且立刻省算力和审核量。

**怎么做**：失败提议存「负知识」表，记死路 + 失败分类 + 边界。同时当去重键用。

### 第 5 优先：修正传播

**为什么**：这是让审核成本**不随知识库规模线性增长**的唯一杠杆。

**怎么做**：override 强制留备注 → 回流；相似规则传播（一条修正带出同类复核）。

### 第 6 优先：淘汰与整合

**为什么**：防长期腐化。前期不紧急，但**必须在设计时留下钩子**（时间戳、访问计数、版本号），否则后期补不上。

**怎么做**：访问频次降权 + 定期 consolidation 去重合并 + versioned records。

### 明确不做（现阶段）

- **全自动闭环**：2026 年无人做到，人在准入环是当前的正确姿势
- **成功信号直接回写知识库**：§4.1 已论证地基是虚的
- **等文献成熟再动手**：这块文献本来就薄，等不到

| **自进化 / Self-Evolving** | 系统在部署后自我改进。至少三支：模型自训练 / 脚手架自改进 / 知识资产演化 |
| **脚手架 Scaffold** | 模型周围的一切：prompt、记忆、工具、工作流。改脚手架 ≠ 改权重 |
| **知识飞轮 Data/Knowledge Flywheel** | 用真实使用产生的信号持续改进系统的闭环 |
| **RAC 飞轮** | Reason → Align → Construct，本体治理飞轮（arXiv:2604.08603，**future work，未部署**） |
| **CAR-RAC** | ⚠️ 不存在的术语。是对 RAC 的误记，勿引用 |
| **静默合理错误 silent plausible error** | 跑得通、看着合理、但答错。text-to-SQL 中约 81% 的错误属此类 |
| **intrinsic self-correction** | 不执行、只重读自己产出的自检。实测贡献仅 1–3 个百分点 |
| **执行式验证** | 真跑，看报错和结果集再修正。效果显著高于 intrinsic |
| **IND / 包含依赖** | Inclusion Dependency，「A 列的值是否都出现在 B 列」。外键发现的形式化基础 |
| **包含率 inclusion coefficient** | `|distinct(A) ∩ distinct(B)| / |distinct(A)|`。严格定义要求 =1，带阈值的叫 partial IND |
| **证据锚定 evidence-anchored** | 强制提议附带可核对的证据与推理轨迹 |
| **fail-closed** | 出问题默认拒绝而非放行。回归门的正确姿势 |
| **experience-following** | 输入相似 → 输出相似 → 坏条目污染新执行的现象 |
| **检索多样性坍缩** | 存得越细，同质查询越漏斗式命中同几条 |
| **负知识 negative knowledge** | 试过但失败的路径，显式留存以防重复探索 |
| **修正传播** | 一次人工修正变成规则，防止同类问题反复进队列 |
| **CQ / 能力问题** | Competency Question，本体应能回答的问题清单，可当验收/回归用例 |
| **OBQC** | Ontology-Based Query Check，用本体规则校验生成的查询 |
| **MMR** | Maximal Marginal Relevance，检索时兼顾相关性与多样性的经典方法 |

## 附录 C：调研方法与证据强度说明

本文由 8 次全景检索 + 4 次 GitHub API 检索 + 5 个定向深挖任务产出（2026-09-01）。以下是诚实的方法学说明。

### 三个未核实的数字

以下三条在网络综述中广泛流传，**本次调研未能在同行评审主源核实**，正文中已标注，此处再次列明：

1. 「48,403 条待审提议 vs 775 个人工决定」的 60:1 积压比
2. 「证据锚定使角色赋值从 36 条压到 4 条」
3. 「审核从 4 分钟/条降到 1 分钟/条」

追溯发现它们被归给 arXiv:2506.08422，但该论文主题是 taxonomy alignment（F1 0.97 vs 人工 0.68），主题与数字均对不上。可能出自附录，也可能是二次综述的拼接。

**方向性判断（生成可 scale、审核不可 scale）是常识性的，且有 GOFlowLLM 等同行评审工作从机制上支持，但这三个具体数字不应被引用。**

### 一处已修正的术语错误

「CAR-RAC 治理飞轮」这个说法**不存在**。原论文（arXiv:2604.08603）中的机制叫 **RAC**（Reason → Align → Construct）。且如正文所述，RAC 在该论文中是未部署的 future work。

### 证据强度分级

| 强度 | 本文中的例子 |
|---|---|
| **严谨 benchmark** | experience-following 错误传播、EvoMemBench 横评、MAC-SQL / DIN-SQL 消融、BIRD 准确率 |
| **同行评审论文** | NVIDIA MAPE、Airbnb AITL、GOFlowLLM、MIBiG 4.0、IND 发现算法 |
| **预印本（未评审）** | DBAutoDoc 的 G1–G8 与 0.75 阈值、RAC、多数 2026 年 arXiv 条目 |
| **实践博客 / 厂商** | 置信度三分法、1–5% 抽检、自适应阈值、队列度量指标 |
| **未核实** | 附录 C 开头的三个数字 |

### 已知的调研盲区

- GitHub 关键词搜索很粗，本体工程生态大量项目挂在 Protégé / LinkML / OWL / 生信工具链名下，未被覆盖。「生态密度差四个数量级」的结论应打折看
- OpenViking 的记忆单元真实 schema 未读到源码（核心在未开源部分），「无状态机」的判断基于 README 和可见目录，未能证实

- KG decay / ontology bloat 缺少严谨对照实验，相关结论多为定性
