## 前言:为什么"能画出来"离"能用"很远

力导向图的入门门槛极低。`d3-force` 三十行代码就能让一堆点自己排开、边自己拉直,截图放进 PPT 相当好看。

然后你会依次撞上这些墙:

1. 节点到几百个,**标签开始互相压**,图还在视图内但已经读不出信息
2. 用户拖了一个节点,**松手它弹回去了**——因为力学还在跑
3. 用户拖好了整张图,**刷新全没了**
4. 你想给它写测试,发现**布局是有状态迭代、点击是浏览器 hit-test**,两样都不像能测的东西
5. 你终于写了浏览器取证脚本,**它给你的表是错的**,而你差点照着去改好的代码

前四条是工程问题,业界有成熟答案。第五条最阴险,也最少被写进文档——本文第五部分专门讲它。

## 第一部分:力导向布局算法

### 1. 弹簧-斥力模型与 O(n²) 瓶颈

力导向布局(force-directed / spring embedder)的核心比喻:

- **边 = 弹簧**,把相连的节点往一起拉
- **节点 = 同极电荷**,互相推开
- 迭代求解直到系统能量最低

问题出在斥力:每个节点都要跟**其他所有节点**算一次斥力,单帧 O(n²)。1000 个节点就是每帧一百万次计算,而你需要几百帧才能收敛。

这是力导向布局的**主要瓶颈**——不是渲染,是力的计算。

### 2. Barnes-Hut:把 O(n²) 降到 O(n log n)

Barnes-Hut 本是天体物理的 n-body 近似算法,思路直接:

> 远处一团节点,不必逐个算斥力,**用它们的质心代替**。

实现上用四叉树(2D)或八叉树(3D)递归划分空间。判断"够不够远"靠一个阈值 θ(barnes-hut theta):离得远就用质心,离得近就递归下去精算。

复杂度从 O(n²) 降到 **O(n log n)**。这是几乎所有严肃实现的默认配置——`d3-force` 的 `forceManyBody()` 内部就是 Barnes-Hut,`theta` 默认 0.9。

**三个必须知道的代价:**

- **小图上可能反而更慢**。近似有固定开销,ForceAtlas2 的作者明确说它"在小网络上可能是反生产力的",所以提供开关。Gephi 和 sigma.js 都把 `barnesHutOptimize` 暴露成一个标志位。
- **内存变大**。四叉树本身要存。BatchLayout 的基准测试里,Gephi 的 ForceAtlas2BH **因内存耗尽在两个大图上直接失败**。
- **布局质量会下降**。用 stress、邻域保持率等指标衡量,近似版不如精确 O(n²) 版。但大图上没人用精确版。

原作者对形状的说法值得记:除了近似本身的副作用,**Barnes-Hut 不改变布局的整体形状**。也就是说它是个纯性能优化,不是另一种布局。

### 3. ForceAtlas2 与它的真实上限

ForceAtlas2(Jacomy et al., PLoS ONE 2014)是 Gephi 的默认布局,也是这个领域最常被引用的工程化方案。作者态度很诚实——**他们不声称理论创新**,而是把几项已有技术整合好:

- Barnes-Hut 近似
- **度数相关的斥力**(degree-dependent repulsion):度数高的节点推得更开,显著减少视觉杂乱
- 局部 + 全局**自适应温度**(adaptive temperature)控制收敛

设计目标写得很清楚:**无标度网络,10 ~ 10,000 节点**。

而实践中 Gephi 里的 ForceAtlas2 能对 **~100,000 节点**出好布局——超出原论文的设计目标一个数量级。这个落差值得留意:论文说的是"设计给多大",工具能跑的是"极限到多大",两个数字不该混用。

### 4. 再往上:多层粗化、降维、GPU

超过 ForceAtlas2 能力范围的图,业界几条路:

| 方案 | 思路 | 代表 |
|---|---|---|
| **多层粗化**(multilevel coarsening) | 反复把图缩成更小的图,在粗层上先求解,再逐层细化 | 经典多层方法,Gephi/OpenOrd 系 |
| **批并行多核** | 把力计算批量化并行 | BatchLayout / BatchLayoutBH,比 ForceAtlas2(BH) 快很多且质量相当或更好 |
| **降维** | 把图布局问题转成降维问题 | DRGraph |
| **流式 + GPU** | 流算法配 GPU 加速 | BigGraphVis |
| **采样近似** | 随机采样做 O(n) 力计算 | Gove (2019),作为 Barnes-Hut O(n log n) 的替代 |
| **快速多极子** | FMM | Greengard |

对绝大多数业务场景:**你不会走到这一步**。走到了,先问是不是应该少画一些节点(见第三部分)。

### 5. 纯力学的通病:布局不可复现、语义不可控

这两条是力导向的固有缺陷,值得单独讲,因为它们不靠换库解决。

**不可复现**:初始位置随机 + 迭代过程 → 同一份数据每次刷新出来的图不一样。用户建立的空间记忆("客户那一坨在左上")每次刷新都失效。

**语义不可控**:力学只认拓扑(谁连谁),不认语义(谁属于哪个业务域)。结果是同域实体散落各处。

业界常见的三类应对:

1. **固定随机种子** + 固定初始位置 → 至少可复现
2. **叠加语义力**:给每个节点算一个"目标位置"(按域分扇区、按层级分行),用 `forceX`/`forceY` 往目标点**拉**。注意是拉不是钉——保留力学微调,强连通的节点仍会互相靠近,看得出连接紧密程度。直接赋坐标就退化成静态圆环/分层布局了。
3. **换非力学布局**:层次数据用 dagre/ELK,大规模用 UMAP 类降维

第 2 条是性价比最高的,也是本项目采用的。**一个细节容易漏:** 目标点和力参数(`distance`/`charge`/`collide`)都是**图坐标下的绝对值**。想把布局整体铺开,只放大目标点是没用的——节点会被原样的斥力和碰撞半径重新挤回原来的密度。三者必须同步缩放。

## 第二部分:渲染器决定你的天花板

这一节的核心结论:**最大的性能因素是渲染技术,不是库的 API。**

### 1. SVG / Canvas / WebGL 三层对比

| | SVG | Canvas | WebGL |
|---|---|---|---|
| 每个节点 | 一个 DOM 元素 | 一张位图上的像素 | GPU 顶点 |
| 样式 | CSS,最灵活 | 代码绘制 | 写 shader |
| 命中测试 | 浏览器原生 | 自己算 | 自己算 |
| 天花板 | 最低 | 中 | 最高 |
| 瓶颈 | DOM 树大小 | 主线程 CPU | 文字渲染 |
| 可达性 | ✅ 屏幕阅读器可读 | ❌ 需开发者补文本 | ❌ 同 Canvas |
| 自动化可测 | ✅ 选择器直接点 | ❌ 只有一个元素 | ❌ 同 Canvas |

最后两行经常被漏掉,而它们可能是你的**决定性约束**——见本节第 5 小节。

### 2. 同行评议的真实数字

Zhao 等人(*Visual Computing for Industry, Biomedicine, and Art*, 2025)在 481 个图数据集上测了 D3.js、ECharts.js、G6.js 跨 SVG/Canvas/WebGL,节点规模 100 ~ 200k,边/点比 1 ~ 10。

**以交互中维持 30 FPS 为标准,最大节点数:**

| 组合 | 30 FPS 下的最大节点数 |
|---|---|
| D3-SVG | ~2,000 |
| ECharts-SVG | ~2,000 |
| ECharts-Canvas | ~3,000 |
| D3-Canvas | ~5,000 |
| D3-WebGL | ~7,000 |

整体排序:D3-WebGL > D3-Canvas > D3-SVG > G6-Canvas > ECharts-Canvas ≈ ECharts-SVG > G6-SVG。

**另一组数字**:Sigma.js(WebGL)的实践估计上限在 **100,000 ~ 500,000 节点**,取决于边密度和硬件。5,000 ~ 50,000 节点区间 Sigma.js 和调优过的 vis-network 都能用;超过 50,000,不做服务端预渲染或 LOD 采样的话 Sigma.js 是唯一实际选项。

⚠️ **这两组数字差一个数量级,不要混用。** 学术数字量的是"带标签和命中测试、交互中持续 FPS",厂商/实践数字量的是"裸渲染能力"。前者更接近你的用户体验,后者更接近宣传页。

还有一条跨库通用:**边数大幅增加会让所有库的渲染性能都劣化。** 报节点数不报边密度的基准,参考价值有限。

### 3. 文字是 WebGL 的软肋

Horak 等人(2018)的对比里有个反直觉发现:**WebGL 的性能下降只在显示文字标签时出现。**

原因是 GPU 渲染文字本身不擅长(要么走纹理图集,要么走 SDF,都有成本)。于是出现了**混合方案**:图形元素用 WebGL,文字用 Canvas 叠一层。

实践含义:如果你的图**必须显示标签**(业务图谱基本都必须),WebGL 的优势会被显著削弱。先量一下带标签的帧率再决定。

### 4. 主流库定位

| 库 | 渲染器 | 适合 |
|---|---|---|
| **Cytoscape.js** | Canvas | 把图当**分析对象**:内置算法、布局、中心度、路径查找。科研/网络分析工作流 |
| **Sigma.js** | WebGL(+ graphology 数据层) | 图大到"WebGL 渲染和数据层比内置算法更重要" |
| **vis-network** | Canvas | 交互式网络示意图:物理引擎、拖放、聚类、编辑控件 |
| **d3-force** | 自己选(SVG/Canvas) | 外观和行为要**最大程度自定义** |

生态规模差很多:Cytoscape.js 约 50 万 npm 周下载,vis-network 约 20 万,Sigma.js 约 5 万。文档和社区支持严重偏向 Cytoscape 和 D3。Memgraph 的一次评估就是这样:他们发现 SigmaJS 渲染大图确实明显更快,但**文档匮乏 + D3 更流行**,最后没选它。

**实用规则:分析用 Cytoscape,示意图用 vis-network,大规模 WebGL 渲染用 Sigma。**

另外一个常被忽视的事实:**d3-force 是布局,不是渲染器。** 你完全可以用 d3-force 算力、把坐标流给 WebGL 渲染——这是常见的混合模式,也意味着"选 d3-force"和"选 SVG"是两个独立决定。

### 5. 被低估的一条:可测性与可达性

前面四小节都在讲性能。但有两种约束会**直接否决**性能最优选项:

**可测性。** Canvas 和 WebGL 整张图是**一个** DOM 元素。你的 E2E 脚本没法 `click("[data-id='node_42']")`——只能算出屏幕坐标再合成点击,而合成点击有它自己的问题(见第五部分第 2 小节)。如果你的验收手段是浏览器自动化,SVG 的"每节点一个 DOM"是压倒性优势。

**可达性。** Canvas 输出对屏幕阅读器**完全不可见**,除非开发者额外补文本替代;WebGL 同理。SVG 尽管天花板低,在这点上保有优势。如果你的产品有无障碍要求,这条可能不是权衡而是硬门槛。

> 这是一个容易被"选型就是选性能"框住的地方。**验收手段和合规要求可以反向决定技术选型**,而且它们通常比性能更难绕过——性能不够可以少画节点,可达性不够没法糊弄。

## 第三部分:先坏的不是你以为的那个指标

### 1. "看不见"与"看不清"差一个数量级

问"节点变多会怎样"时,大多数人第一个想到的是**节点跑到视图外**。但如果你的实现有自适应缩放(fit-to-view),这其实是**最晚出现**的问题。

先崩的是**可读性**。给一组参考量级(自适应缩放 + 径向布局,单画布约 900×620):

| 节点 | 画布外 | 最近邻间距 |
|---|---|---|
| 58 | 0 | 62.5 px |
| 200 | 0 | 32.5 px |
| 800 | 0 | **14.0 px** |
| 1600 | 0 | 7.5 px |
| 3200 | 167 | 4.9 px |

节点半径通常 6~19px(按度数)。所以 **800 节点时圆圈已经互相贴住,而"跑出视图"要到 ~1600 才发生**——可读性瓶颈早一个数量级。

这个落差的实践含义很直接:**用户抱怨"图看不清"的时候,放开最小缩放是错的修法。** 那只是让他看一张更小的蚂蚁图。

> 通用教训:定位规模瓶颈时,把"几何可见性"和"感知可读性"分开量。前者好算,后者才是用户感受到的。

### 2. 规模应对手段的优先级

按 ROI 排序,而不是按技术含量排序:

1. **少画**——按域折叠、N 跳邻域、度数过滤、搜索定位。**这是唯一能解决可读性的一类**,其他都只解决性能
2. **聚合渲染**——把一团低度数节点画成一个"云",点开才展开
3. **LOD**(level of detail)——缩小时不画标签、不画细边
4. **换 Canvas / WebGL**——解决帧率,不解决看不清
5. **换布局算法**(BatchLayout / DRGraph / GPU)——解决布局耗时,不解决前两样
6. **服务端预计算布局**——解决首屏,不解决交互

注意 4、5、6 不解决第 1 条要解决的问题。**如果用户的抱怨是"看不清",从 1 开始;如果是"卡",从 4 开始。** 搞反了会花大力气换渲染器,然后发现图还是读不出信息。

## 第四部分:交互状态的工程难点

这部分是踩坑集中区,几乎每条都不难但都不明显。

### 1. 拖拽固定与力学的冲突

`d3-force` 用 `fx`/`fy`(fixed x/y)钉住节点。标准教程写法是:拖拽开始设 `fx`/`fy`,拖拽结束**清空**它们。

结果是**松手节点弹回去**。如果你还叠了语义力(往目标点拉),弹回得更干脆——用户白拖。

要"拖到哪留哪",就是**松手不清 fx/fy**。代价:

- 这个函数叫 `unpin` 却不真的 unpin,**命名和行为不一致**,要在注释里讲清
- 需要提供一个"全部解钉"入口(重置按钮),否则用户没法回到力学布局
- 解钉全部时**必须重新加热** `alpha`。此时模拟已收敛(alpha 衰减到 alphaMin),只调 `restart()` 而不抬 alpha,节点根本不动——表现是"重置按钮没反应"

### 2. 坐标系:三套坐标必须分清

有缩放平移之后,同一个点有三种坐标:

| 坐标系 | 含义 | 谁用 |
|---|---|---|
| **屏幕坐标** | 鼠标事件给你的 `clientX/Y` | 事件处理 |
| **容器坐标** | 减掉容器 `getBoundingClientRect()` 的偏移 | 命中测试 |
| **图坐标** | 反变换掉 translate/scale | 力学模拟(`fx`/`fy` 存的是这个) |

最常见的 bug:**拖拽时把屏幕坐标直接喂给 `pin()`**。缩放不是 1 的时候,节点会以 k 倍速度跟手飞走。必须先反变换:

```
图坐标 = (屏幕坐标 - translate) / scale
```

第二个坑:**滚轮缩放要以鼠标位置为锚点**,不是以画布中心。做法是缩放后调整 translate,使鼠标下的那个图坐标点保持在原屏幕位置。否则用户觉得图在"乱跑"。

第三个坑(React 特有):**`onWheel` 是 passive 的**,里面 `preventDefault()` 无效——缩放的同时整页跟着滚。必须用原生 `addEventListener("wheel", fn, { passive: false })`。

### 3. 布局持久化的三个陷阱

把用户摆好的布局存下来(localStorage / 后端),三个坑:

**① 读写两头各自硬编码结构。** 存的时候手写一个对象字面量,读的时候手写解析——将来改格式只改一头,就**静默分叉**:存进去读不回来,而表现只是"手工布局莫名失效",没有任何报错。**修法:写一对 pack/unpack 函数 + 往返测试**(pack 再 unpack 应等于原值)。

**② 存的是绝对坐标,而画布尺寸会变。** 用户在 876×817 的画布上摆好布局,全屏后画布变成 1920×1080——旧坐标和按新画布重算的目标点混在一起,布局一团乱。两种修法:

- **等比缩放**:按新旧尺寸比例缩放存档坐标。问题是长宽比一变只能取一个比例(压扁或留白),而且缩放后的点跟新的目标点仍不在同一坐标系
- **记下尺寸,不匹配就不套用**:存档里记下当时的画布尺寸,尺寸变了就放弃存档、走默认布局,**并明确告知用户**

后者更诚实,代价只是换画布后手工布局失效一次。选哪个取决于你的用户是不是经常改窗口。

**③ 兜底值参与了判定。** 这条最隐蔽。画布尺寸通常要等 `ResizeObserver` 量出来,所以代码里会有个兜底初值(比如 `{900, 620}`)。如果第一轮就拿这个**猜的**尺寸去比对存档,而真实尺寸是 876×817,那么**用户只要刷新一下就会误报"尺寸变了"**。

> 通用原则:**兜底值可以用来渲染,不可以用来做判定。** 判定拿假输入得出的是假结论。
>
> 而且这类 bug **单测天然看不见**——测试固件里尺寸总是显式传进去的,永远走不到兜底那条路。只有真浏览器能暴露。

**④ 顺带一条格式迁移的判断**:如果老版存档的结构可以被识别成"过期",让它判过期、下次保存原地覆盖,就**不需要写迁移代码,也不留一个永远没人清的旧版本键**。别急着给存储键升版本号。

### 4. 收敛时机与视觉突变

力导向默认异步收敛:`d3-force` 挂 `on("tick")`,每帧回调,几百帧后停。

问题:**收敛过程中点云的形状在变,而你的自适应缩放停在旧值。** 用户看到的是"先一张巨图,停几秒突然缩到正常"。

出现时机是**点云形状要变**的每个时刻:首屏、重置布局、数据刷新。

修法:在这些时刻**同步跑完收敛再交坐标**(`sim.tick(n)` 手动推 n 步,不派发事件所以对外静默),调用方当场就能算出最终缩放。300 步对几十个节点约几十毫秒,只在这几个时刻付。

**一个反向的坑:不要用 `on("end")` 触发自适应缩放。** 它每次收敛都触发——用户拖完节点松手也算一次——挂了就变成"每拖一下视图自己缩放一次"。视图该只在你明确想动的时刻动。

## 第五部分:图交互怎么测

这部分是本文最想传达的。图可视化常被当成"只能人眼验收"的领域,于是测试覆盖长期为零。其实可以分层。

### 1. 分层:哪些是纯函数,哪些必须真浏览器

关键动作是**把判断从渲染组件里搬出来**。

| 类别 | 例子 | 怎么测 |
|---|---|---|
| **纯函数** | 配色、图例、度数、连通分量、边分类、边几何(路径字符串)、坐标变换、搜索排序、存档打包 | 普通单测,毫秒级 |
| **有状态但有合同** | "松手后 fx/fy 是什么"、"解钉全部后有几个节点被钉住" | 暴露一个测试缝(手动推进 n 步 + 读快照),仍是单测 |
| **必须真浏览器** | 命中测试、事件时序、布局美观、帧率 | E2E / 视觉回归 |

第二类最容易被误判。"力学模拟是有状态迭代,所以不写单测"——这个结论对"布局美不美观"成立,对"`unpin` 之后 `fx` 是 null 还是数字"**不成立**,那是个纯粹的输入输出合同。

> **把一个正确的结论用在错误的范围上,代价是那部分代码的 bug 无人能发现。**
>
> 判断有多少能被测,取决于它**住在哪个文件里**。如果你的项目没有 jsdom(或者你不想为组件测试付那个复杂度),那么写在组件里的判断就是零覆盖。搬进纯函数模块是零新基建的修法。

### 2. 合成事件测不出真实竞态

这是最容易产生**假绿**的地方。

考虑一个真实 bug:搜索框下面一个候选下拉,点击候选项"有时有反应有时没有"。非确定性 = 竞态。

常见写法是 `onBlur={() => setTimeout(() => closeList(), 120)}`(延时关,好让 `onClick` 先跑)。真相是:

- **`blur` 在 `mousedown` 那一刻就触发**,计时器随即启动
- 按住鼠标超过 120ms,列表已经卸载
- 而**浏览器只在 down/up 落在同一个仍挂载的元素上才派发 `click`**
- 手一顿就超 → 随机失灵

**用合成事件测这个,永远是绿的。** `element.click()` 直接调 handler,绕过真实 hit-test;自动化的 mousedown → click 全在**同一毫秒**,远在 120ms 窗口内。

正确修法也值得记:`onMouseDown` 里 `preventDefault()` 让输入框**根本不失焦**,计时器不存在。**延时关只是把时间窗放宽(治标),不失焦才是没有窗口。**

> 教训:**判据要落在真实路径上。** 合成事件能给你一张全绿的表,而 bug 好好地待在那儿。
>
> 如果你的自动化框架无法合成"慢速真实点击"(很多 CDP allowlist 不开放 Input 域),退一步用**必要条件**做判据——比如"输入框有没有失焦",配回滚对照组。

### 3. 判据必须先验区分力

比合成事件更阴险的一类:**判据根本不可能返回真,于是它永远绿。**

一个真实例子:验"操作后应该弹出提示"。脚本先读节点坐标、再查提示文本,报"应弹提示却没弹"。看起来是代码 bug。

实际上提示 6 秒后自动消失,而脚本读坐标那几步已经花掉了时间——**查的时候早没了**。提示一直都在弹(改成 150ms 高频轮询,33/33 次都看到)。

这里有个双重危害:不光那两个红灯是假的,**同一批里的绿灯也是假的**——那些 ✅ 用的是同一个空转判据,它当时根本不可能返回 yes。

> 纪律:
> 1. **拿到红灯,先问"我的判据有区分力吗",再问"代码对不对"。** 验法:手工注入一个应当被判为真的东西(比如一个含该文案的 div),看判据能不能返回真。
> 2. 对瞬态 UI,判据从"此刻在不在"改成"**这段时间出现过没有**"——进入前先装轮询器。
> 3. **判据空转时,整批结论都不可信**,不只是变红的那几个。

### 4. 变异测试与固件的规模/形状

变异测试(手动改坏实现,看测试是否变红)是验断言强度的好手段。但在图这个领域,**"变异存活"经常不是断言的锅,是固件的锅**:

- **规模不对**:12 节点的固件下,改不改"铺开系数"最近邻间距都恒定(碰撞半径主导,力的作用还没显形)。换到几十个节点才显形
- **形状不对**:验"同步收敛"时用手搓的规则圆环点云,它**首帧就已经接近终局**(终局/首帧 ≈ 0.93),所以"预热 1 步"和"预热 300 步"看不出差别。换成真实布局算法的输出(比值 1.42),变异立刻死
- **判据层次不对**:断言"缩放系数 < 1"看似合理,但如果 fit 算法的 padding 本身就让它是 0.89,这个断言**恒真**

> **变异存活 ≠ 断言不敏感。** 先问"我的固件能让这个变异表现出来吗"。**固件的规模和形状都是判据的一部分。**
>
> 一个实用做法:固件的规模和形状尽量取**真实数据的统计特征**(节点数量级、边/点比、度数分布),而不是好看的规则图形。

### 5. 生产级做法:视觉回归与 E2E

上面讲的是"不用重基建能做到什么"。生产上还有两层:

**视觉回归测试**(Percy / Chromatic / Playwright 的 `toHaveScreenshot`):截图比对基线。

- 优势:能抓"布局变丑"这种没法写断言的问题
- **难点是力导向的不确定性**:布局不可复现 → 每次截图都不一样 → 全是假阳性。必须先**固定随机种子 + 固定初始位置 + 同步收敛固定步数**,把布局变成确定性的,视觉回归才有意义
- 还要配容差阈值(抗字体渲染差异)

**E2E**(Playwright / Cypress):

- Playwright 的 `mouse.move/down/up` 能做**带真实时序的慢速拖拽**,这是能抓第 2 小节那类竞态的手段
- Canvas/WebGL 图的 E2E 明显更难:没有选择器可点,得自己算屏幕坐标。SVG 在这里的优势很实际
- 给节点挂 `data-*` 属性(id、域、度数)是成本最低的可测性投资

**取证脚本自身的纪律**(不分层级都适用):

1. **不许吞 stderr,且要先验退出码。** 一个"匹配到多个元素"的硬失败被吞掉,脚本会继续跑、读到上一轮的残留状态,给你一张看起来像结论的表
2. **配回滚对照组**。改动后全绿不算证据——把改动回滚掉,判据必须变红。没变红说明它测的不是你以为的东西
3. **区分"证据"和"哨兵"**。有些判据在回滚态**也成立**(走的是另一条早退路径),它们不能计入定罪,只能当哨兵

## 第六部分:本项目当前实现 vs 生产

本项目(一个本体/知识图谱学习项目)当前是 **d3-force 3.0 + 自写 SVG**,58 节点 / 91 边。

| 维度 | 本项目 | 生产级 | 差距 |
|---|---|---|---|
| **布局算法** | d3-force(内含 Barnes-Hut)+ 自写径向语义力 | ForceAtlas2 / 多层粗化 / BatchLayout | ⭐⭐⭐⭐ 几十节点上没有差别 |
| **渲染器** | SVG,每节点一个 DOM | Canvas(Cytoscape)/ WebGL(Sigma) | ⭐⭐⭐ 58 节点毫无压力;800+ 才需要动 |
| **规模应对** | 无折叠/无 LOD/无 N 跳邻域,只有搜索定位 | 折叠 + LOD + 服务端预布局 | ⭐ **最大的真实退化点**。已测得 800 节点即"看不清" |
| **布局确定性** | 初始位置 = 算好的目标点 + 同步收敛固定步数 → 确定性 | 同 + 固定种子 | ⭐⭐⭐⭐ 这条意外地接近生产,因为它是视觉回归的前提 |
| **持久化** | localStorage + 尺寸闸门 + pack/unpack 往返测试 | 后端存储、多用户、多视图命名保存 | ⭐⭐ 单机单用户够用,没有共享/协作 |
| **纯函数测试** | 单测行数约为实现的 1.7 倍,一百多个用例 | 同等或更高 | ⭐⭐⭐⭐ 这条不打折 |
| **组件测试** | **无**(项目无 jsdom) | React Testing Library 覆盖交互 | ⭐ 接线层零覆盖,靠把判断搬进纯函数规避 |
| **视觉回归** | **无** | Percy / Chromatic 基线比对 | ⭐ 布局"变丑"无人报警 |
| **E2E** | 手写浏览器取证脚本,一次性,用完删 | Playwright 套件进 CI | ⭐⭐ 取证质量不低(配回滚对照组),但**不可重放、不在 CI** |
| **可达性** | SVG + `<title>`,无键盘导航、无 ARIA | 键盘可达 + 屏幕阅读器可用 | ⭐ 只占了 SVG 的天然便宜,没有主动投入 |
| **性能监控** | 无 | FPS 埋点、布局耗时上报 | ⭐ |

**补齐路线(按 ROI 排序):**

1. **按域折叠 / N 跳邻域**——唯一能解决可读性的一类。触发条件明确:节点数上到 200~300 就该做
2. **Playwright 套件进 CI**——把一次性取证脚本变成可重放资产。当前最大的工程债
3. **视觉回归基线**——布局已经是确定性的,这条的前置条件已经满足,成本比想象低
4. **键盘导航 + ARIA**——如果要给他人使用
5. 换 Canvas/WebGL——**800 节点之前不要碰**,收益为零而失去可测性和可达性

**一句话总结退化点:** 纯函数层接近生产水准,**规模应对和可重放的自动化测试是两个真实缺口**,而渲染器这条常被当成首要任务的事,在当前规模下 ROI 为零。

## 附录 A:术语小词典

| 术语 | 含义 |
|---|---|
| **力导向布局**(force-directed layout) | 把边当弹簧、节点当同极电荷,迭代到能量最低的布局方法。别名 spring embedder |
| **Barnes-Hut** | n-body 近似算法。用四/八叉树把远处节点团近似成质心,斥力计算从 O(n²) 降到 O(n log n) |
| **theta(θ)** | Barnes-Hut 的距离阈值,决定"多远才能用质心近似"。d3-force 默认 0.9。越大越快越不准 |
| **ForceAtlas2** | Gephi 默认布局。Barnes-Hut + 度数相关斥力 + 自适应温度。设计目标 10~10,000 节点 |
| **度数相关斥力** | 度数高的节点斥力更大,把枢纽节点推开以减少视觉杂乱 |
| **alpha / alphaMin / alphaTarget** | d3-force 的"温度":alpha 从 1 衰减到 alphaMin 即停。alphaTarget 是衰减的目标值。**已收敛后想让节点再动,必须重新抬 alpha** |
| **tick** | 力学模拟的一帧。`sim.tick(n)` 手动推 n 步且**不派发事件**(对外静默) |
| **fx / fy** | d3-force 的固定坐标。非空 ⟺ 该节点被钉住,力学不再改它 |
| **fit-to-view** | 自适应缩放:算出包住所有节点所需的缩放和平移 |
| **LOD**(level of detail) | 按缩放级别减少细节(缩小时不画标签/细边) |
| **多层粗化**(multilevel coarsening) | 反复把图缩小求解再逐层细化,大图布局的主流手段 |
| **hit-test** | 命中测试:判断鼠标点在哪个元素上。SVG 浏览器原生做,Canvas/WebGL 要自己算 |
| **变异测试**(mutation testing) | 故意改坏实现,看测试是否变红,用来验断言强度 |
| **视觉回归测试** | 截图与基线比对。力导向图需先让布局确定化,否则全是假阳性 |
| **passive 事件监听** | 浏览器优化:passive 监听里 `preventDefault()` 无效。React 的 `onWheel` 是 passive 的 |
| **stress / 邻域保持率** | 布局质量的量化指标:图论距离与画布距离的吻合程度 / 近邻关系被保留的比例 |

## 写在最后

如果这份文档只留五条,我希望是这五条:

1. **渲染器决定天花板,但可测性和可达性可以反向决定渲染器。** 性能不够可以少画节点,可达性不够没法糊弄
2. **先崩的是"看不清",不是"看不见"。** 800 节点就读不出信息,而跑出视图要到 1600。用户抱怨看不清时,放开缩放是错的修法
3. **判断住在哪个文件里,决定它能不能被测。** 把判断搬出渲染组件、变成纯函数,是零新基建的最高 ROI 投资
4. **兜底值可以用来渲染,不可以用来做判定。** 这类 bug 单测天然看不见,只有真浏览器能暴露
5. **取证脚本自己就是最大的假结论来源。** 合成事件、宽选择器、被吞的 stderr 都能给你一张看起来像结论的表。不吞 stderr、先验退出码、判据先验区分力、配回滚对照组

最后一句送给所有要做图可视化的朋友:**这个领域的教程密度极高而工程文档密度极低。** 三十行画出第一张图的门槛低到不像话,而"拖动不弹回、刷新不丢、能测、能读"这些事,每一条都得自己踩。希望这份能让你少踩几个。
