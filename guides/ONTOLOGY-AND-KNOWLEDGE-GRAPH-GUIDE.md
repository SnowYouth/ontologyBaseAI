## 1. 问题是什么：为什么需要本体和知识图谱

### 1.1 数据库能存数据，但不"懂"数据

一个关系数据库能存下海量数据，也能用 SQL 查得飞快。但它有一个天生的短板：**它只知道"数据怎么存"，不知道"数据是什么意思"。**

举个例子。数据库里有两张表 `table_A` 和 `table_B`，中间靠一个外键连着。数据库知道的全部信息是："这两张表能 JOIN"。它不知道：

- `table_A` 代表的是"客户"这个**现实世界的概念**
- `table_B` 代表的是"账户"
- 它们之间的关系是"一个客户**拥有**一个或多个账户"
- 而且有条规矩："账户不能凭空存在，必须挂在某个客户下"

这些"意思"和"规矩"，散落在开发者的脑子里、需求文档里、代码的注释里，**唯独不在数据库里**。新人接手要靠口口相传，机器更是完全无从得知。

### 1.2 当关系变复杂，SQL 就开始吃力

只有一两层关系时，JOIN 够用。但现实领域的关系往往是**多层、网状、还带规矩**的。当你要回答这类问题：

- "和某个实体有 N 跳内关联的所有实体是哪些？"
- "这条关系链上有没有违反某条业务规矩的地方？"
- "根据已知的几条事实，能不能推出一条没有明写的事实？"

用 SQL 写会变成层层嵌套的递归 JOIN，既难写又慢，而且**推理能力是 SQL 天生不具备的**。

这就是本体（Ontology）和知识图谱（Knowledge Graph）要解决的问题：**把"领域是什么意思、有什么规矩、怎么关联"这份知识，从人脑和文档里搬出来，变成机器能读、能查、能推理的结构。**

### 1.3 一句话定位

| 技术 | 管什么 |
|---|---|
| 数据库 schema | 数据**怎么存**（效率导向） |
| 本体 Ontology | 领域**是什么意思**（语义导向） |
| 知识图谱 KG | 本体（规矩）+ 真实数据（实例），能查能推理 |

后面几节会把这三者的关系彻底讲透。

## 2. 四个核心概念：schema / 本体 / 实例 / 知识图谱

这四个词经常被混着说，先一次性厘清。它们是一条**从"怎么存"到"什么意思"再到"填上数据"的链条**：

```
schema(存储层)  →  本体(语义层/规矩)  →  灌真实数据  →  知识图谱 KG(规矩+数据)
数据怎么存          领域是什么意思          实例化           能查能推理的成品
```

### 2.1 用 Java 类比一次讲清（本体 vs KG）

如果你有面向对象背景，一个类比几乎完美对应：

```java
// ===== 这部分 = 本体 (Ontology / TBox / 规矩层) =====
class Reader   { ... }          // 领域里有"读者"这种类型
class Card     { ... }          // 有"借书卡"这种类型
class Borrower { ... }          // 有"借阅人/借阅记录"这种类型
// 关系:Reader 拥有 Card,Card 挂 Borrower
// 约束:一个 Borrower 必须挂在某张 Card 下

// ===== 这部分 = 知识图谱 (KG / ABox / 数据层) =====
Reader c = new Reader("张三");            // 一个具体的读者对象
Card   a = new Card("借阅卡");
c.拥有(a);                                // 一条具体的关系
```

- **本体 = 那些 `class` 声明**：定义"世界上有哪些类型的东西、它们之间能有什么关系、有什么规矩"。**不含任何具体数据。**
- **KG = `new` 出来的对象和它们的连线**：把真实的实例灌进去，连成一张网。

一句口诀：**本体是规矩（class），KG 是数据（对象）。**

### 2.2 TBox 与 ABox（学术术语，但很好用）

正式文献里，这组区分有专门的名字，源自描述逻辑（Description Logic）：

| 术语 | 全称 | 是什么 | 对应 Java |
|---|---|---|---|
| **TBox** | Terminological Box | 概念层：类、关系、约束 | class 定义 |
| **ABox** | Assertional Box | 断言层：具体实例和事实 | new 出来的对象 |

**本体 = TBox。知识图谱 = TBox + ABox。** 记住这个，读任何本体论文都不会晕。

### 2.3 本体不是"用完就丢的中间品"

一个常见误解是把本体当成"通往 KG 的垫脚石，KG 建好就没用了"。**错。** 本体和 KG 是"模具 vs 铸件"的关系，模具要长期留着：

1. **KG 长大时照着它继续灌。** 新数据进来，靠本体保证"合规矩"（新来的也得是合法的类型、合法的关系）。
2. **它是 KG 的质检标准。** 有人灌了一条违反规矩的边（比如跳过中间层直连），本体一比对就能发现。没有本体，KG 就是一坨没人管对错的点线。
3. **它让机器能推理。** 本体里写了"账户必属于某客户"，那哪怕数据漏了这条边，机器也能推出来——这是 KG 比普通数据库值钱的核心，而这个能力来自本体。

所以：**最终交付的是 KG，但本体作为骨架长期活在 KG 里，不丢。** 行业里常把两者合起来叫，就因为它俩分不开：**KG = 本体（骨架）+ 实例数据（血肉）。**

### 2.4 本体 ≠ 数据库 schema 的翻版（最关键的区分）

初学最容易犯的错：把数据库表结构直接照抄成本体。两者管的根本不是一回事：

| | 数据库 schema | 本体 |
|---|---|---|
| 服务对象 | 机器读写效率 | 人和机器的语义共识 |
| 会不会为性能扭曲 | 会（分表、冗余、中间表） | 不会（只关心概念） |
| 例子 | `reader_0`~`reader_9` 十张分表 | 就一个概念：`读者` |
| 约束完整性 | 常为灵活性故意不建外键 | 显式声明所有业务约束 |

数据库为了性能会做的那些事——水平分表、冗余字段、加中间关联表、塞各种状态码——**全是存储噪音，不是概念**。从 schema 到本体，要做三件"提纯"：

1. **去存储噪音**：分表、冗余、纯技术的中间表、序列表，砍掉，不是概念。
2. **补隐性关系**：外键是明写的关系，但大量业务关系埋在**代码和约定**里，schema 根本看不见。
3. **加规则**：本体带完整约束，而 schema 的约束往往为了灵活性故意不全。

> 记住这句：**数据库 schema 是本体的重要原料，但绝不能照抄。**

## 3. 本体到底以什么形式存在

初学者最常卡的一个问题：本体到底是一段代码、一个文件、还是一个库？

答案：**本体本质是"信息"（一份关于领域概念的结构化知识），但它总要落成某种形式才能存在。** 就像"一份合同"本质是约定，但得落成一张纸 / 一个 PDF 才能被人读、被存档。

同一个本体，可以用好几种形式承载，从"最正式"到"最随手"：

| 形式 | 长什么样 | 谁在用 |
|---|---|---|
| **① 一个文件**（最主流） | 文本文件，后缀 `.owl` / `.ttl` / `.rdf` / `.jsonld`，里面用特定语法写满类、关系、约束 | 企业 / 学术标准做法 |
| **② 一个库里的数据** | 存进专门的**三元组库 / 图库**（GraphDB、Neo4j、Fuseki 等），当数据查 | 规模大、要频繁查询时 |
| **③ 一段代码** | Python 的 class 定义、dict、或 Pydantic 模型，把概念直接写成代码结构 | 轻量项目 / 嵌进程序里 |
| **④ 一张图 / 一张表** | 白板、Excel、脑图 | 起草期，还没正式化 |

**关键认知：同一个本体，这四种形式可以互相转换。** 它不绑死在任何一种上。"本体 = 一个文件"只是它最常见的**存储态**，不是它的本质。

### 3.1 同一个本体，两种形式对照

以一个"三层实体模型"（读者 → 借书卡 → 借阅记录，图书馆 / 电信 / SaaS 里都常见的通用结构）为例。

**形式①：正式文件（Turtle 语法，`.ttl` 文件）**

```turtle
:Reader   a owl:Class .
:Card     a owl:Class .
:Borrower a owl:Class .

:hasCard     a owl:ObjectProperty ;
             rdfs:domain :Reader ;      # 读者 —拥有→ 借书卡
             rdfs:range  :Card .
:hasBorrower a owl:ObjectProperty ;
             rdfs:domain :Card ;        # 借书卡 —挂→ 借阅记录
             rdfs:range  :Borrower .
```

这就是一个真实本体文件的样子——**纯文本，记事本能打开**。每一行都是一条"关于概念的声明"。

**形式③：代码（Python dict，轻量）**

```python
ONTOLOGY = {
    "classes": ["Reader", "Card", "Borrower"],
    "relations": [
        {"name": "hasCard",     "from": "Reader", "to": "Card"},
        {"name": "hasBorrower", "from": "Card",   "to": "Borrower"},
    ],
    "constraints": [
        "每个 Borrower 必须挂在一张 Card 下",
    ],
}
```

**两段东西表达的是同一个本体**，信息完全等价，只是一个走标准文件、一个走 Python 代码。

### 3.2 该选哪种形式

| 你的场景 | 建议形式 |
|---|---|
| 要和外部系统 / 标准生态互通、要正式发布 | `.owl` / `.ttl` 文件（走 W3C 标准） |
| 规模大、关系复杂、要图查询和推理引擎 | 图库 / 三元组库（物化） |
| 轻量项目、嵌进已有程序、快速迭代 | Python dict / Pydantic（代码） |
| 还在探索"该建什么"阶段 | 先画图 / Excel，别急着上语法 |

三元组（Triple）是最底层的通用表达：**任何本体和 KG，无论用哪种形式，本质都能拆成一堆 `(主语, 谓语, 宾语)` 三元组**，比如 `(客户, 拥有, 账户)`。这就是 RDF（Resource Description Framework）的核心，也是"三元组库"名字的来历。

## 4. 本体怎么建：三条路线 + 经典七步法

### 4.1 三条建模路线

| 路线 | 怎么做 | 优点 | 缺点 | 代表 |
|---|---|---|---|---|
| **① 自顶向下** (top-down) | 领域专家先拍顶层大概念，再逐层细化 | 权威、规整 | 容易脱离真实数据，落地时和库对不上 | FIBO（金融）、Cyc |
| **② 自底向上** (bottom-up) | 从已有数据 / schema / 文档里**抽**实体和关系，归纳成概念 | 贴数据、能落地 | 容易把存储噪音当语义 | 数据驱动的 schema 归纳 |
| **③ 中间开花** (middle-out) | 先定几个核心概念当"种子"，再双向扩展 | 工程上最实用 | 需要种子选得准 | 大多数落地项目 |

**实战里几乎都是③中间开花。** 因为纯顶向下会脱离真实数据，纯底向上会淹没在噪音里。中间开花的做法是：**先用一个现成的领域骨架（如果有）当种子，再连着真实数据双向印证和扩展。**

> 小提示：如果你的领域已经有**成熟的行业模型 / 标准**（金融有 FIBO，电信有 TMF SID，电商有 schema.org），别从零归纳——直接拿它当顶层骨架，这就是七步法第 2 步"找复用"。行业替你把最难的顶向下那一半做完了。

### 4.2 经典七步法（Ontology 101）

斯坦福的 *Ontology Development 101* 是本体工程的经典入门方法论，任何本体都可以套这七步：

```
1. 定范围    —— 这个本体要回答哪些问题?(先划边界,别贪大)
2. 找复用    —— 有没有现成本体可借(FIBO / schema.org / 行业标准)?别重造轮子
3. 列术语    —— 把领域里所有名词摊开(客户 / 账户 / 订购 / 账单…)
4. 定类+层级 —— 哪些是类,谁是谁的子类(个人客户 ⊂ 客户)
5. 定关系/属性—— 类之间怎么连(客户 —拥有→ 账户),每个类有哪些属性
6. 加约束    —— 基数、必填、值域(一个账单必属于一个账户)
7. 填实例    —— 灌真实数据,变成 KG
```

**注意分界线：第 1~6 步产出的是本体（TBox / 规矩层），第 7 步才碰真实数据、变成 KG（ABox）。** 这条线和前面"本体 vs KG"完全对应。

### 4.3 起手式：能力问题（Competency Questions）

七步法第 1 步"定范围"最容易空对空。现代做法有个非常实用的抓手，叫**能力问题（Competency Questions, CQ）**：

> **先列出"这个本体 / 系统建好后，要能回答哪些具体的业务问题"，用这些问题反推需要哪些概念、哪些数据。**

例如：

- "某个客户名下有几个欠费的账户？"
- "某个服务实例（号码 / 账号）属于哪个客户？"
- "某个账户下挂了哪些服务实例？"

这些 CQ 是把"漫无边际的大领域"收敛成"我到底该建什么"的**漏斗**。尤其面对一个有成千上万张表的巨型数据库时，CQ 就是那个"靶子"——**先有靶子再开枪**，避免盲目地把所有表都拉出来却不知道哪些有用。CQ 也是下一节 LLM 建本体流程的标准起手式。

## 5. 2026 年怎么建：LLM 起草 + 人审校

### 5.1 老问题：本体瓶颈（the ontology bottleneck）

本体工程从上世纪 90 年代就成熟了（七步法、Protégé 编辑器都是那时的产物），但它几十年没能真正大规模落地。根本原因就一个词：**贵**。

一个中等规模的企业本体，需要一队领域专家花几周到几个月手工建模。领域专家稀缺、时间贵、还容易在细节上扯不清。这个"建本体太慢太贵"的死结，业界直接叫它 **the ontology bottleneck（本体瓶颈）**。

### 5.2 新范式：LLM 是起草者，不是作者

2023 年 LLM 成熟后，本体工程领域第一个反应就是"终于有工具能捅破这个瓶颈了"。到 2025–2026，最强共识已经形成，一句话概括：

> **LLM 是"起草者"（draft generator），不是"作者"（autonomous author）。人负责审校和拍板。**

这套流程叫 **human-in-the-loop（人在环中）/ expert-in-the-loop（专家在环中）**：

```
LLM 读数据 / schema / 文档  →  生成本体草稿(类、关系、约束)
              ↓
   领域专家审校、修正、拍板   ← 这一步不能省,省了就出幻觉和垃圾概念
              ↓
        迭代扩展 / 灌数据成 KG
```

**为什么不能全自动？** 2026 的综述给出的现状是：**绝大多数方案仍是"半自动"的**，无论生成还是扩展。这既说明"保留人在环里很重要"，也坦承"技术还没成熟到能全自动"。LLM 会**编概念（幻觉）**，会把存储噪音误当语义，只有懂领域的人能拦住。

### 5.3 两大技术流派（对应第 4 节的路线）

2026 的大综述把 LLM 建本体切成两派，正好对应自顶向下 vs 自底向上：

| 流派 | 怎么做 | 对应路线 | 特点 |
|---|---|---|---|
| **Schema-Based**（顶向下） | 先喂 LLM 一个预定义本体骨架，让它照骨架抽取 / 扩展 | 自顶向下 | 一致性高但死板 |
| **Data-Driven**（底向上） | 不给骨架，让 LLM 从原始数据 / 文本里归纳出本体 | 自底向上 | 灵活但容易把噪音当概念 |

代表工作：Schema-Based 有 KARMA（多智能体框架）、Kommineni 的 `CQ → TBox → ABox` 管线；Data-Driven 有 GraphRAG、OntoRAG。**实战都是两者混着来**（middle-out），跟第 4 节的结论一致。

### 5.4 三个 2026 关键实践

1. **CQ（能力问题）是起手式。** 现在主流管线第一步不是画类图，而是让 LLM 先生成一批能力问题，用问题来锚定范围（第 4.3 节讲过）。

2. **企业级有专门框架了。** 针对企业库出现了 OntoEKG 等 LLM 驱动的本体构建框架。但作者也坦承一个坑：**目前连"怎么评判本体建得好不好"的标准 benchmark 都还没有**——这个领域仍很新。

3. **幻觉 + 上下文窗口是两大拦路虎。** 把大型结构化标准直接塞给 LLM，它会编概念、而且窗口塞不下。2026 的解法是用 GraphRAG 式的检索 + 闭环管线来喂，而不是一次性灌。

### 5.5 你需要的两个角色

落地一次 LLM 建本体，最小配置就两个角色：

- **AI（起草者）**：读 schema / 文档，产出本体草稿、CQ、映射建议。
- **领域专家（审校者）**：判断草稿对不对、砍掉噪音概念、补上藏在业务里的隐性规矩、最终拍板。

这两个角色缺一不可，而且**领域专家是不可替代的那个**——这不是凑合的土办法，而是 2026 学术界和工业界公认的正确姿势。

## 6. 数据规模问题：亿级数据要不要灌进 KG

### 6.1 一个必然会撞到的疑问

真实系统里，很多表是千万级、上亿行的（流水、日志、明细）。初学者很自然会问：**这么大的数据，灌进知识图谱现实吗？**

答案：**全量灌既不现实、也没必要、还是错的做法。** 三个理由，一个比一个致命：

1. **物理上撑不住。** 图库存上亿节点 + 几十亿条边，存储和查询性能会爆，成本极高。亿级行是关系库的主场，不是图库的。
2. **业务上没意义。** KG 的价值是表达复杂关系、支持推理，不是当第二个数据仓库。把亿级流水灌进去，得到的是一坨没人查的垃圾——那些数据用 SQL `WHERE` 查更快。
3. **概念上搞反了。** 亿级大表几乎全是**事实流水**（"发生了什么事"），不是**实体和关系**（"是什么、归谁、连着谁"）。KG 要的是后者。

### 6.2 关键区分：哪些数据该进 KG

这是全部答案的核心——按"是实体关系，还是事实流水"分两类：

| | **实体 / 关系表**（该进 KG） | **事实 / 流水表**（不进 KG） |
|---|---|---|
| 例子 | 客户主表、账户表、产品目录、组织机构 | 交易流水、账单明细、操作日志 |
| 特征 | "是什么、归谁、连着谁" | "某时刻发生了一笔什么事" |
| 数量级 | 通常几万~几百万 | 亿级，每天还在涨 |
| 变化 | 慢变（不常改） | 只增不改，爆炸增长 |
| 归谁管 | KG / 本体 | 关系库 / 数据仓库，SQL 查 |

**"上亿的大表"99% 落在右边这列，它们本来就不该进 KG。** 核心实体（客户 / 账户 / 产品）的数量级通常可控。

### 6.3 数据不进 KG，但 KG 要够得着：三种姿势

1. **只灌实体，流水留在原地（最主流）。** KG 里只放节点和关系，明细流水留在关系库，需要时按 ID 回查。图定结构、DB 取实况，各干各的。
2. **采样 / 切片。** 不灌全库，只圈一个小切片（比如"一个客户 + 他名下所有账户和服务实例"，几十个节点），用于教学、验证、demo。
3. **抽象汇总，不存明细。** 如果某些流水的**统计结论**对关系有用（如"某客户是高价值客户"这个标签，从亿级流水算出来），KG 里只存那个结论标签，不存算它的原始数据。

### 6.4 一句话收束

```
       ┌─────────── KG (图库/本体) ───────────┐
       │  只存:实体 + 关系 + 慢变属性 + 汇总标签  │   ← 可控规模
       └───────────────┬──────────────────────┘
                       │ 需要明细/实时时,按 ID 回查
                       ↓
       ┌─────────── 关系库 / 数仓 ─────────────┐
       │  亿级流水:交易、明细、日志(留在原地)     │   ← SQL 查
       └──────────────────────────────────────┘
```

**KG 是"骨架 + 索引"，不是"数据的第二份拷贝"。** 骨架轻，所以亿级流水的存在完全不构成问题——它们根本不上骨架。这个"实体上图、流水留库"的分工，直接引出了下一节的两大流派。

## 7. 两大流派：物化 KG vs 虚拟 KG（OBDA）

知识图谱怎么"存在"，业界分成两大流派。这个区分直接决定了架构、成本和适用场景。

### 7.1 物化 vs 虚拟

| | **物化 KG (Materialized)** | **虚拟 KG / OBDA (Virtual)** |
|---|---|---|
| 数据 | **灌**进图库，存一份拷贝 | **不动**，留在原关系库 |
| 查询 | 直接查图库 | 本体把查询翻译成 SQL，回原库查 |
| 新鲜度 | 有延迟（要同步） | **实时**（直接查活库） |
| 亿级大表 | 灌不动 | **无所谓，本来就没搬** |
| 深度推理 | **强**（图库主场） | 弱（多跳翻 SQL 是灾难） |
| 适合 | 关系复杂、要深推理、数据慢变 | 数据量大、要实时、库已存在 |

### 7.2 虚拟 KG 的正式名字：OBDA / VKG

"数据留在关系库，本体架在库之上当一层语义映射，查询时翻译成 SQL 回库查"——这个范式有正式名字（两个名，一回事）：

- **OBDA** = Ontology-Based Data Access（基于本体的数据访问）
- **VKG** = Virtual Knowledge Graph（虚拟知识图谱）

"Virtual（虚拟）"点破了本质：**KG 是"虚"的——它逻辑上存在（你能按图的方式提问），物理上不存在（没真建一张点线网），数据始终在原库。**

这恰好完美回答了第 6 节"亿级数据灌不动"的顾虑：**OBDA 路线下数据本就不搬，所以规模再大也不构成问题。**

### 7.3 别二选一：生产是混合的

物化和虚拟不是对立的，成熟的大型系统往往**两条腿走路**：

- **慢变 + 要深度推理**的实体关系（如组织架构、产品拓扑）→ 物化进图库
- **海量 + 要实时**的数据（如客户实时余额、当日流水）→ 虚拟映射回库查

这就是知识图谱、语义层、实时数据库"三条腿缝合"在架构上的真实长相。

## 8. OBDA 深入：本体当语义层，AI 照着写 SQL

OBDA 在 LLM 时代变得格外重要，值得单独拆开讲——因为它几乎是"带本体护栏的 Text-to-SQL"，和 AI agent 天然契合。

### 8.1 它怎么工作

```
用户问:"某客户名下有几个欠费的账户?"
        ↓
本体(语义层):知道"客户""账户""欠费"这些概念 = 映射到库里的哪些表/列
        ↓
翻译成 SQL:SELECT ... FROM 客户表 JOIN 账户表 ... WHERE 余额 < 0 AND 客户名 = ?
        ↓
回原库查 → 返回真实、实时的数据
```

中间"本体映射到表 / 列"这一层，是 OBDA 的核心资产。业界有国际标准来写这层映射：

- **R2RML / RML** — W3C 标准，专门描述"关系表 → 本体概念"的映射规则。
- **Ontop** — 最有名的开源 OBDA 引擎，吃 R2RML 映射，能自动把 SPARQL（图查询语言）重写成 SQL。

### 8.2 和 LLM / Text-to-SQL 的关系

LLM 天生**不会写"你的库"的 SQL**——因为它不知道你的库长什么样（有哪些表、字段叫什么、怎么关联）。这正是 Text-to-SQL 最大的难点。

OBDA 的本体，恰好就是喂给 LLM 的那份"库长啥样 + 概念怎么映射"的知识：

| OBDA 组件 | 在 LLM Text-to-SQL 里的作用 |
|---|---|
| 本体的类和关系 | 告诉 LLM 领域有哪些概念、怎么关联 |
| 概念→表/列映射 | 告诉 LLM 每个概念落在哪张表、哪个字段 |
| 本体的约束 | 当护栏，防 LLM 编造不存在的表名 / 字段（减少幻觉） |

所以在 2026，**OBDA + LLM = 带语义层护栏的 Text-to-SQL agent**，是当下 "GraphRAG / semantic layer over LLM" 的一大分支，也是数据分析圈"语义层（semantic layer）"（dbt / Cube / Looker 那套 metrics layer）的知识图谱化表达。

### 8.3 OBDA 的两个代价（天下没有免费午餐）

选虚拟路线要清楚它的短板，别被"数据不用搬"冲昏头：

1. **深度推理弱。** 一两跳关系（客户→账户→服务实例）翻译成 JOIN 很顺。但"找出所有和某实体有 6 跳内关联的实体"这种深图遍历，翻译成 SQL 就是递归 JOIN 灾难——又慢又难写。**深关系推理是物化图库的主场，虚拟路线啃不动。**
2. **映射本身是工作量。** "概念→表 / 列"这层映射得有人建、有人维护。表结构一改，映射就得跟着修。这活儿省不掉——只是从"灌数据"换成了"写映射"。

### 8.4 什么时候选 OBDA

选 OBDA（虚拟）当满足：数据已经在关系库里、数据量大 / 要实时、关系深度不超过几跳、且愿意维护映射层。

选物化图库当满足：需要深度多跳推理 / 图算法（社区发现、路径分析、图嵌入）、数据相对慢变、且能接受同步延迟。

大多数真实系统最终是**两者混合** —— 用 OBDA 覆盖海量实时数据，用物化图库覆盖需要深推理的核心关系。

## 9. 生产环境真实选型

### 9.1 本体表达语言

| 语言 / 格式 | 严格度 | 适用 |
|---|---|---|
| **OWL**（Web Ontology Language） | 最严格，支持复杂推理 | 需要形式化推理的正式本体（医疗、金融） |
| **RDFS**（RDF Schema） | 中等，轻量类型和层级 | 大多数够用的场景 |
| **SKOS** | 弱，管概念词表 / 分类法 | 术语表、主题词表 |
| **属性图 schema**（Neo4j 等） | 灵活，非形式化 | 工程导向、不追求形式推理 |
| **自定义**（JSON / dict / Pydantic） | 自定 | 轻量项目、嵌进程序 |

**严格度是个旋钮，不是越严越好。** OWL 能做复杂推理，但学习和维护成本高；很多工程项目用 RDFS 甚至属性图 schema 就够。按"实际要不要形式化推理"来选。

### 9.2 存储 / 引擎

| 类别 | 代表 | 说明 |
|---|---|---|
| 三元组库（RDF 原生） | GraphDB、Apache Jena Fuseki、Blazegraph | 存 RDF 三元组，SPARQL 查询，支持推理 |
| 属性图库 | Neo4j、TigerGraph、NebulaGraph | 工程友好，图算法丰富，Cypher / GSQL 查询 |
| OBDA 引擎（虚拟） | Ontop、Stardog（含虚拟能力） | 不存图，把 SPARQL 重写成 SQL 查关系库 |
| 语义层 / metrics layer | dbt Semantic Layer、Cube | 数据分析圈的"轻量本体"，管指标定义和映射 |

### 9.3 建模工具

- **Protégé** — 斯坦福出品的老牌本体编辑器，OWL 建模事实标准，有可视化界面。
- **LLM + 编辑器插件** — 2026 趋势，如 Protégé 的 GPT 插件，让 LLM 起草、人在编辑器里审校。

### 9.4 选型速查

| 场景 | 推荐组合 |
|---|---|
| 正式企业本体、要推理、要互通 | OWL + Protégé + 三元组库（GraphDB / Stardog） |
| 工程项目、要图算法、不追求形式推理 | 属性图 schema + Neo4j |
| 数据已在关系库、要实时、量大 | OBDA：本体 + Ontop（或 LLM Text-to-SQL）回查原库 |
| 学习 / 轻量 / 快速迭代 | Python dict/Pydantic 表达本体 + 直接查库 |

## 10. 常见误区

**误区 1：本体就是数据库 schema 的翻版。**
错。schema 管存储效率（会分表、冗余），本体管领域语义（只关心概念）。schema 是原料，不能照抄。（见 2.4）

**误区 2：本体建好了就没用了，KG 才是产物。**
错。本体是 KG 的骨架和质检标准，长期共存、持续约束新数据。KG = 本体 + 实例。（见 2.3）

**误区 3：知识图谱要把所有数据都灌进去。**
错。只灌实体和关系，亿级流水留在关系库 SQL 查。KG 是骨架不是数据拷贝。（见第 6 节）

**误区 4：本体必须是 `.owl` 文件、必须用 OWL。**
错。本体可以是文件、库、代码、图，四种形式等价可转换；严格度按需选，OWL 只是最严格的一档。（见第 3、9 节）

**误区 5：LLM 能全自动建本体。**
错。2026 的共识是 LLM 起草 + 人审校（human-in-the-loop）。LLM 会幻觉、会把噪音当概念，领域专家不可替代。（见第 5 节）

**误区 6：虚拟 KG（OBDA）什么都能干，比物化好。**
错。OBDA 深度推理弱，多跳遍历翻 SQL 是灾难。深推理是物化图库主场。生产多为混合。（见第 7、8 节）

**误区 7：面对大库，先把所有表拉出来再说。**
错。先用能力问题（CQ）锁定"要回答什么"，反推需要哪些表——先有靶子再开枪。（见 4.3）

## 11. 附录

### 11.1 术语词典

| 术语 | 全称 / 英文 | 含义 |
|---|---|---|
| 本体 | Ontology | 领域概念、关系、约束的形式化规格（规矩层） |
| 知识图谱 | Knowledge Graph, KG | 本体 + 实例数据连成的点线网（规矩 + 数据） |
| TBox | Terminological Box | 本体的概念层（类、关系、约束） |
| ABox | Assertional Box | 具体实例和事实（数据） |
| 类 | Class / Concept | 一种类型的东西（如"客户"） |
| 实例 | Instance / Individual | 类的一个具体对象（如"客户张三"） |
| 关系 | Relation / Object Property | 类与类之间的连接（如"拥有"） |
| 属性 | Attribute / Data Property | 类自身的字段（如"客户姓名"） |
| 约束 | Constraint / Axiom | 规矩（如"账户必属于某客户"） |
| 三元组 | Triple | `(主语, 谓语, 宾语)`，本体 / KG 的最小表达单元 |
| RDF | Resource Description Framework | W3C 的三元组数据模型标准 |
| RDFS | RDF Schema | 轻量的类型 / 层级本体语言 |
| OWL | Web Ontology Language | 最严格、支持复杂推理的本体语言 |
| SPARQL | — | 查询 RDF / 图数据的语言（类比图世界的 SQL） |
| OBDA | Ontology-Based Data Access | 本体架在关系库上、翻译成 SQL 回查的范式 |
| VKG | Virtual Knowledge Graph | OBDA 的别名，强调"KG 是虚拟的" |
| 物化 | Materialized | 把数据真的灌进图库存一份 |
| R2RML / RML | — | W3C 标准，描述"关系表→本体概念"映射 |
| Ontop | — | 开源 OBDA 引擎，SPARQL→SQL 重写 |
| CQ | Competency Question | 能力问题，用于锁定本体范围的业务问题 |
| 语义层 | Semantic Layer | 数据分析圈对"轻量本体 / 映射层"的叫法 |
| human-in-the-loop | — | 人在环中，LLM 起草 + 人审校的协作模式 |
| Protégé | — | 斯坦福老牌本体编辑器 |
| 本体瓶颈 | ontology bottleneck | 手工建本体太慢太贵，几十年难落地的死结 |
